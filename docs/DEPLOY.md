# Разворачивание BusCom ERP

Боевой контур: один сервер, три контейнера — Postgres, одноразовый накат миграций, приложение. HTTPS на текущем хостинге терминирует провайдер, поэтому Caddy вынесен в необязательный профиль. Всё описано в `docker-compose.prod.yml`.

**Контур поднят 2026-09-20.** Что работает и что осталось — в разделе «Текущее состояние» в конце.

> **Где хостить.** PRD, «Нефункциональные требования»: персональные данные клиентов лежат на сервере **в РФ** (Selectel, Timeweb, Yandex Cloud). Зарубежный хостинг для боевого контура не подходит. Демо-стенд без реальных данных — можно где угодно.

## Что нужно на сервере

- Linux с Docker и плагином Compose (`docker compose version` отвечает);
- домен админки (например `erp.bus-com.ru`), доведённый до сервера — способ зависит от хостинга, см. «Домен и HTTPS»;
- 1.5 ГБ RAM достаточно: приложение на ~10 пользователей плюс Postgres. **Образ при этом должен собираться не здесь** — `next build` требует больше гигабайта и на такой машине его убивает OOM-killer. Сборка живёт в GitHub Actions, сервер только скачивает готовый образ;
- 10 ГБ диска: образы приложения, база и выгрузки бэкапов. Этого хватает только при уборке: каждый выкат приносит два новых образа, и без очистки диск кончается за несколько выкатов (так и случилось 20.09 — `pull` упал с «no space left on device»). Деплой теперь чистит образы и кэш сборки **до** скачивания; прошлые версии живут в GHCR, а не на диске, и при откате скачиваются заново.

Порт Postgres наружу не публикуется — в базу ходит только приложение внутри сети compose.

## Первый запуск

**0. Подготовить сервер (Ubuntu 22.04)**

От root, один раз:

```bash
curl -fsSL https://raw.githubusercontent.com/etisnow/buscom-erp/main/scripts/server-setup.sh -o server-setup.sh
less server-setup.sh          # прочитать перед запуском — он ставит пакеты и включает firewall
bash server-setup.sh
```

Скрипт идемпотентен: ставит Docker из официального репозитория, заводит пользователя `deploy` (без пароля, вход только по ключу, состоит в группе `docker`), клонирует репозиторий в `/opt/buscom-erp`, открывает в `ufw` SSH и `APP_PORT` (по умолчанию 81). Секреты не создаёт и контейнеры не запускает — это дальше и руками.

Если SSH проброшен на нестандартный внешний порт, проверьте, какой порт слушает sshd **внутри** сервера: `ss -tlnp | grep sshd`. Правило `ufw allow OpenSSH` открывает 22 — если внутри другой порт, доступ можно себе отрезать.

**0.1. Домен и HTTPS**

Зависит от того, есть ли у сервера выделенный IP.

**Вариант А — хостинг сам проксирует 80/443 (так устроен Джино.VPS).** Провайдер принимает запросы к привязанным доменам, терминирует TLS своим сертификатом и отдаёт их на внутренний порт VPS, проставляя `X-Forwarded-For` и `X-Forwarded-Proto`. Тогда:

- Caddy не нужен и порты 80/443 занять не сможет — он вынесен в профиль `caddy` и по умолчанию не поднимается;
- приложение слушает внутренний порт из `APP_PORT` (в панели Джино это «Проксирование портов 80/443 → Порт по умолчанию»; значения должны совпадать);
- домен привязывается к серверу в панели хостинга, там же подключается бесплатный SSL-сертификат («Домены → Настройки домена → SSL»);
- `BETTER_AUTH_URL` всё равно `https://erp.bus-com.ru` — снаружи схема https, даже если до контейнера запрос доходит по http.

**Вариант Б — выделенный IP, HTTPS поднимаем сами.** A-запись `erp.bus-com.ru` → IP сервера, проксирование у провайдера для этого IP выключено, контур поднимается с профилем Caddy:

```bash
docker compose -f docker-compose.prod.yml --env-file .env.production --profile caddy up -d --build
```

В `.env.production` тогда `APP_PORT=127.0.0.1:3000`, чтобы приложение не торчало наружу мимо Caddy. Без A-записи сертификат не выпустится: Let's Encrypt проверяет владение доменом по HTTP на порту 80. Проверить: `dig +short erp.bus-com.ru`.

**1. Код на сервер**

Если `server-setup.sh` уже отработал, репозиторий лежит в `/opt/buscom-erp` — этот шаг пропускается. Вручную:

```bash
git clone https://github.com/etisnow/buscom-erp.git
cd buscom-erp
mkdir -p backups
```

**2. Переменные окружения**

Создайте рядом `.env.production` — он в `.gitignore`, в репозиторий не попадёт. Список переменных приложения — в `.env.example` и в `src/server/env.ts` (там же схема проверки: при нехватке обязательной переменной контейнер падает на старте, а не позже).

```dotenv
# Домен админки — для Caddy (вариант Б) и для ссылок в письмах
ERP_DOMAIN=erp.bus-com.ru

# Внутренний порт, на который хостинг проксирует 80/443 (вариант А).
# Должен совпадать со значением в панели провайдера.
# Для варианта Б с Caddy: APP_PORT=127.0.0.1:3000
APP_PORT=81

# Postgres внутри compose
POSTGRES_USER=buscom
POSTGRES_PASSWORD=<длинный случайный пароль>
POSTGRES_DB=buscom_erp

# Приложение. Хост postgres — имя сервиса из compose
DATABASE_URL=postgresql://buscom:<тот же пароль>@postgres:5432/buscom_erp
BETTER_AUTH_SECRET=<32+ случайных символов>
BETTER_AUTH_URL=https://erp.bus-com.ru
SITE_WEBHOOK_SECRET=<32+ случайных символов, тот же на стороне сайта>

# Почта для сброса пароля — запасной путь. Основной — раздел «Почта»
# в /admin/dictionaries: что введено там, то и действует, эти переменные тогда не нужны.
# Ни там, ни здесь не задано — письма не уходят, ссылка пишется в лог контейнера.
SMTP_HOST=
SMTP_PORT=587
SMTP_SECURE=false
SMTP_USER=
SMTP_PASSWORD=
SMTP_FROM="BusCom ERP <noreply@bus-com.ru>"

# Первый администратор — используется один раз при сиде.
# На боевом сервере значение может отличаться от примера: почту администратора
# меняли после запуска. Действующее — командой из раздела «Логин и пароль
# администратора» выше; здесь адрес намеренно не записан, репозиторий публичный.
SEED_ADMIN_EMAIL=admin@bus-com.ru
SEED_ADMIN_NAME=Администратор
SEED_ADMIN_PASSWORD=<временный пароль, сменить после первого входа>
```

Секреты генерируются так:

```bash
openssl rand -base64 36
```

Файл должен быть доступен только владельцу: `chmod 600 .env.production`.

**3. Запуск**

Штатный путь — ручной запуск workflow `Deploy` (см. «Автодеплой»): он соберёт образы и выкатит их сам. Если поднимаете руками на машине, где хватает памяти для сборки:

```bash
docker compose -f docker-compose.prod.yml --env-file .env.production up -d --build
```

Порядок задан зависимостями: Postgres поднимается и проходит healthcheck → контейнер `migrate` накатывает миграции и завершается → стартует `app`. Если миграции упали, приложение не стартует — это сознательно, чтобы оно не работало на старой схеме.

**4. Первый администратор**

```bash
docker compose -f docker-compose.prod.yml --env-file .env.production run --rm migrate pnpm db:seed
```

Сид идемпотентен: существующего пользователя не трогает. Он же заводит демо-каталог товаров — для боевой базы это, скорее всего, лишнее, тогда заводите товары через `/products`.

**5. Проверить**

```bash
# на самом сервере — приложение на внутреннем порту
curl -I http://127.0.0.1:81/login             # 200

# снаружи — через домен
curl -I https://erp.bus-com.ru/login          # 200 и сертификат валиден
curl -I https://erp.bus-com.ru/orders         # 307 на /login — защита работает

docker compose -f docker-compose.prod.yml logs -f app
```

Если внутри сервера отвечает, а снаружи нет — дело не в приложении, а в привязке домена, проксировании портов или firewall.

Дальше — войти, сменить временный пароль, завести сотрудников на `/admin/users`.


## Автодеплой из GitHub Actions

`.github/workflows/deploy.yml` выкатывает `main` на сервер. Запускается не по пушу, а по событию `workflow_run` — **только после зелёного CI**: сломанная сборка до сервера не доедет. Есть и ручной запуск (`workflow_dispatch`) — для первого выката и для отката; он разрешён с `main` или с тега, с других веток job не стартует.

**Ветки.** Повседневные коммиты идут в `development`, в `main` вливаем по просьбе владельца — только этот мерж и выкатывает. CI гоняется на обеих ветках, деплой реагирует лишь на прогон по `main` (`branches: [main]` у `workflow_run` смотрит на ветку прогона CI). Подробности — `docs/DECISIONS.md`, запись «Работа идёт в `development`, выкат — только из `main`».

Что делает на сервере: `git reset --hard` на выкатываемый коммит (разворачивается ровно то, что прошло CI, локальные правки на сервере затираются), `docker compose pull`, затем `up -d --no-build`, затем ждёт, пока приложение действительно ответит на `/login` через опубликованный порт. Если за 150 секунд не ответило — job падает и печатает последние 80 строк лога. Прошлая версия при неудачном выкате остаётся работать: контейнер подменяется только после успешного `pull`.

Проверка живости идёт `curl`'ом с хоста, а не `docker compose exec`. Это не придирка: `exec -T` читает stdin, а этим же stdin на сервер подаётся сам скрипт деплоя — команда съедала его остаток, скрипт молча обрывался и шаг засчитывался успешным при нерабочем приложении. В удалённом скрипте всем командам, способным тронуть stdin, добавлен `< /dev/null`.

### Секреты и переменные репозитория

Заводит их человек — агенту приватный ключ не показывают и в переписку не вставляют.

**1. Ключ для выката** (на своей машине, не на сервере):

```bash
ssh-keygen -t ed25519 -C "github-actions-deploy" -f ~/.ssh/buscom_deploy -N ""
```

Публичную часть (`~/.ssh/buscom_deploy.pub`) — в `/home/deploy/.ssh/authorized_keys` на сервере. Приватную (`~/.ssh/buscom_deploy`) — в секрет репозитория.

**2. Ключ хоста**, чтобы Actions не доверял первому встречному. Порт указывать обязательно, если он нестандартный, — запись в `known_hosts` привязана к паре «хост:порт»:

```bash
ssh-keyscan -t ed25519 -p <порт> <хост>
```

**3. Завести в репозитории:**

```bash
gh secret set DEPLOY_SSH_KEY < ~/.ssh/buscom_deploy
gh secret set DEPLOY_HOST --body "<хост>"
gh secret set DEPLOY_USER --body "deploy"
ssh-keyscan -t ed25519 -p <порт> <хост> | gh secret set DEPLOY_KNOWN_HOSTS

gh variable set DEPLOY_PORT --body "<порт>"            # если не 22
gh variable set DEPLOY_PATH --body "/opt/buscom-erp"   # необязательно, по умолчанию так же
```

`DEPLOY_PORT` и `DEPLOY_PATH` — переменные (`vars`), а не секреты: они не тайна, а в логах job'а их видно, и это помогает разбираться.

### Образ собирается в Actions, а не на сервере

`next build` требует больше 1 ГБ памяти. На боевой машине 1.5 ГБ без swap (OpenVZ — swap не добавить), и сборка там гарантированно падает: проверено, ядро убило процесс.

```
OOM killed process 25 (next-build (v16) total-vm:35081280kB, anon-rss:1116628kB
```

Поэтому job `build` собирает оба образа на раннере GitHub и публикует в GHCR:

- `ghcr.io/etisnow/buscom-erp/app:<sha>` — приложение;
- `ghcr.io/etisnow/buscom-erp/migrate:<sha>` — Prisma CLI для миграций и сида.

Сервер делает только `docker compose pull` и `up -d --no-build`. Ему не нужны ни исходники для сборки, ни память под неё.

Пакеты приватные, и постоянных учётных данных на сервере нет: перед `pull` деплой логинит сервер в GHCR токеном `GITHUB_TOKEN`, который живёт только во время прогона, передаёт его через stdin (в списке процессов он не появляется), а в конце делает `docker logout`.

Ручная сборка на машине, где памяти хватает, никуда не делась: у сервисов остались секции `build`, и `up -d --build` соберёт образы локально.

## Обновление вручную

Если автодеплой не используется или нужно выкатить срочно:

```bash
git pull
docker compose -f docker-compose.prod.yml --env-file .env.production up -d --build
```

Миграции накатятся сами тем же одноразовым контейнером. Простой — несколько секунд на перезапуск `app`; Caddy держит соединения и отдаёт 502 только в этот промежуток.

Откат: `git checkout <прошлый тег>` и та же команда. **Миграции назад не откатываются** — если новая миграция удаляет или переименовывает колонку, откат кода на старую версию её не вернёт. Перед такими миграциями делайте бэкап руками (ниже) и планируйте окно.

## Бэкапы

PRD: ежедневно, хранение 30 дней, копия **вне сервера с базой**.

Скрипт `scripts/backup-db.sh` делает выгрузку в `./backups` внутри тома Postgres и чистит старше 30 дней. Он падает с ненулевым кодом, если файл подозрительно мал, — это повод для алерта.

```bash
chmod +x scripts/backup-db.sh
crontab -e
# каждый день в 03:30 по времени сервера
30 3 * * * cd /path/to/buscom-erp && ./scripts/backup-db.sh >> /var/log/buscom-backup.log 2>&1
```

**Вывоз копии наружу не настроен** — это оставшийся кусок требования PRD. Нужен второй шаг: rsync/rclone в объектное хранилище провайдера (Selectel, Yandex Object Storage) или на другой сервер. Без него бэкап лежит на той же машине и не спасает от её потери.

Восстановление:

```bash
gunzip -c backups/buscom_2026-09-20_0330.sql.gz | \
  docker compose -f docker-compose.prod.yml exec -T postgres psql -U buscom -d buscom_erp
```

PRD требует проверить восстановление **до** запуска. Проверяйте на отдельной пустой базе, а не на боевой.

## Текущее состояние (2026-09-20)

Боевой сервер — Джино.VPS, Ubuntu 22.04.4, OpenVZ: 1 ядро, 1.5 ГБ памяти без swap, 9.8 ГБ диска. Выделенного IP нет.

**Дисковая гигиена.** 20.09 выкат упал на нехватке места: диск был занят на 99%. Уборка образов теперь идёт перед `pull` и в тот же прогон освободила 3,6 ГБ (99% → 62%), после выката — ещё 1,78 ГБ. В логе деплоя печатаются `df -h` до и после и `docker system df`, так что состояние диска видно каждый раз.

**Работает:**

- автодеплой из Actions целиком: сборка образов → публикация в GHCR → выкат на сервер → проверка живости;
- Postgres, миграции и приложение подняты, контейнеры `healthy`;
- приложение доступно снаружи по имени сервера: `https://ba5699d52128.vps.myjino.ru/login` отдаёт 200 — проксирование хостинга и его сертификат в порядке;
- первый администратор заведён сидом, вход проверен живым запросом: 200 и роль ADMIN;
- домен `erp.bus-com.ru` привязан к серверу, SSL подключён (20.09.2026): `https://erp.bus-com.ru/login` — 200 с валидным сертификатом, `/orders` — 307 на вход.

**Осталось: перенаправление http → https.** Сейчас `http://erp.bus-com.ru/login` отдаёт 200 вместо редиректа, а по http **войти нельзя** — и выглядит это обманчиво: страница входа открывается, вход отвечает 200, а каждый следующий клик возвращает на `/login`. Браузер идёт на http, если адрес набран без схемы, так что напороться легко.

Причина не в приложении. `BETTER_AUTH_URL=https://erp.bus-com.ru`, а Better Auth выводит из протокола `baseURL` флаг cookie (`better-auth/dist/cookies/index.mjs`: `baseURLString.startsWith("https://")` → префикс `__Secure-` и `secure: true`). Браузер, открывший страницу по http, такую cookie не сохраняет — молча. Сессии нет ни на одном запросе, `src/proxy.ts` отправляет на вход.

Сертификат уже выпущен, осталось включить перенаправление там же, в настройках домена. Снимать `Secure` через `advanced.useSecureCookies: false` — нельзя: токен сессии админки с ПДн пойдёт по сети открытым текстом.

**Почему домен сначала отдавал 404 — на будущее.** DNS был настроен верно с самого начала: `erp.bus-com.ru` — CNAME на `ba5699d52128.vps.myjino.ru`, тот резолвится в `81.177.135.137`. Отвечал при этом nginx провайдера своей заглушкой. Причина в схеме без выделенного IP: порты 80/443 принимает и терминирует Джино и проксирует на внутренний порт VPS **только для доменов, привязанных к серверу** в панели. Нет привязки — запрос до контейнера не доходит, сколько ни правь DNS-записи. Признак, по которому это узнаётся сразу: по имени сервера 200, по домену 404 от провайдера и чужой сертификат по https.

Полезная мелочь: с машины разработки домен может не проверяться вовсе (VPN hidemy.name режет `bus-com.ru` — нужно исключение). Тогда `curl` покажет таймаут независимо от состояния сервера, и диагностику это собьёт — проверяйте из браузера без VPN.

**Остальные долги по контуру:**

- SMTP не заполнен — письма со сбросом пароля пишутся в лог контейнера;
- вывоз бэкапов за пределы сервера не настроен (PRD требует копию вне машины с БД);
- мониторинг (Sentry/GlitchTip) и алерт «за 3 рабочих часа нет заказов» не настроены;
- сид завёл демо-каталог из 6 товаров — перед реальной работой убрать через `/products`;
- пароль первого администратора лежит в `.env.production` на сервере. Посмотреть: `grep SEED_ADMIN_PASSWORD /opt/buscom-erp/.env.production`. Сменить после первого входа.

**Ловушка формата `.env.production`:** значения с пробелами надо брать в кавычки (`SMTP_FROM="BusCom ERP <noreply@bus-com.ru>"`). Docker Compose разбирает файл и без них, а `source .env.production` в оболочке — нет.

## Импорты на сервере (каталог сайта, картинки)

Скрипты импорта живут в образе миграций. `docker compose run` без имени образа пытается собрать его на сервере и падает по памяти — образ надо указать явно, тот же, что выкатил деплой (`git log -1` на сервере даёт SHA):

```bash
cd /opt/buscom-erp
SHA=$(git rev-parse HEAD)
export MIGRATE_IMAGE=ghcr.io/etisnow/buscom-erp/migrate:$SHA APP_IMAGE=ghcr.io/etisnow/buscom-erp/app:$SHA
docker compose -f docker-compose.prod.yml --env-file .env.production run --rm -T --no-deps \
  -v /opt/buscom-erp/misc:/app/misc migrate pnpm import:site-products misc/site-products.json --dry-run
```

Файлы для импорта кладутся в `/opt/buscom-erp/misc` (с машины разработки: `scp misc/site-products.json buscom-prod:/opt/buscom-erp/misc/`). Сервер видит bus-com.ru, поэтому `import:site-images` качает картинки прямо оттуда.
