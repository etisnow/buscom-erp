# Журнал решений

> Почему сделано именно так. Прежде чем «улучшать» что-то из списка — прочитай причину; если она устарела, предложи изменение человеку и допиши сюда новую запись, а не правь старую.

## 2026-09-19 — Next.js-монолит, а не отдельный бэкенд + SPA

Внутренняя админка на ~10 пользователей: UI, API, вебхуки и серверная логика в одном TypeScript-проекте — один деплой, нет контракта фронт↔бэк, типы от Prisma до формы без генерации клиента. Стек лучше всего знаком AI-агентам. Минусы (SSR почти не нужен, Next навязывает кэширование и границу server/client) приняты. Чтобы при необходимости вынести бэкенд, логика живёт в `src/domain` и `src/server`, а не в компонентах. Подтверждено заказчиком в чате.

Рассмотренные альтернативы: Vite SPA + Hono/NestJS (два приложения), Refine/React-admin (упрёмся в рамки на кастомной логике заказов), Django Admin (быстрый CRUD, но слабый UX для менеджеров).

## 2026-09-19 — Prisma 7.10, а не 8.x

На момент старта npm-тег `latest` у `prisma` указывал на `8.0.0-rc.15` (release candidate), а `@prisma/client` — на 7.10.0. Закреплены согласованные стабильные 7.10.0. Обновлять на 8 — после стабильного релиза, вместе с клиентом и адаптером.

Prisma 7 требует driver adapter (`@prisma/adapter-pg`) и `prisma.config.ts`; клиент генерируется в `src/generated/prisma` (не коммитится, генерируется в `postinstall`).

## 2026-09-19 — Better Auth для входа

Нужны свои пользователи (email + пароль), роли и сессии в своей БД, без внешнего IdP. Better Auth даёт это из коробки с Prisma-адаптером. Регистрация отключена (`disableSignUp`) — пользователей заводит ADMIN. Роль и `isActive` — дополнительные поля пользователя, недоступные для ввода с клиента.

## 2026-09-19 — Деньги в целых копейках

Все суммы — `Int` в копейках (`*Kopecks`), никаких float. Исключает ошибки округления в итогах и оплатах. Рубли только на границе UI (`formatRub`, `rublesToKopecks`). Предел Int (≈ 21 млн ₽ на одно значение) для заказов комплектующих достаточен; если понадобится больше — `BigInt`.

## 2026-09-19 — Статусная машина в домене, а не в БД

Переходы и права по ролям — в `src/domain/order/status.ts`, одна таблица. БД хранит только enum. Сервер проверяет каждый переход через `assertTransition`, UI показывает `availableTransitions`. Добавлены переходы сверх первой версии схемы: AWAITING_PAYMENT → IN_PROGRESS (клиент меняет состав) и отмена из PAID/ASSEMBLY только HEAD/ADMIN.

## 2026-09-19 — Журнал OrderEvent = история + аудит

Каждое изменение заказа пишет `OrderEvent` в той же транзакции. Одна таблица закрывает и ленту в карточке, и требование аудита из PRD. Только добавление, без правок и удалений.

## 2026-09-19 — Позиция заказа хранит снимок товара

`OrderItem` копирует sku/name/price на момент заказа; `productId` — необязательная ссылка. Правки каталога и синхронизация с сайтом не меняют старые заказы.

## 2026-09-19 — Inbox для интеграции

Входящий заказ сначала сохраняется сырым в `IntegrationInbox`, потом разбирается. Уникальность `(source, externalId)` даёт идемпотентность. Цель — не потерять заказ при ошибке маппинга; FAILED разбираются вручную в журнале.

## 2026-09-19 — Бизнес-правила по умолчанию без заказчика

Лимит скидки 10%, рабочее время пн–пт 09–18 МСК, нумерация с 1 и др. (PRD, «Бизнес-правила») выбраны без интервью. Реализовывать как настройки/константы в одном месте, чтобы менять без переделки.

`prisma init` поставил скиллы для нескольких агентов через абсолютные симлинки (ломаются в git и на другой машине). Оставлены обычными папками в `.claude/skills/`: `prisma-cli`, `prisma-client-api`, `prisma-database-setup`.

## 2026-09-19 — shadcn/ui: пресет radix-nova

`pnpm dlx shadcn@latest init -b radix -p nova`. База — Radix UI (не Base UI и не React Aria): у неё больше всего готовых примеров и она лучше всего известна агентам. Пресет Nova — иконки Lucide и шрифт Geist, который уже стоял в проекте. Компоненты лежат в `src/components/ui` и принадлежат проекту: править можно, но при обновлении через CLI правки затрутся — свои обёртки складывать в `src/components/layout` и рядом.

`src/hooks/use-mobile.ts` переписан на `useSyncExternalStore`: версия из шаблона вызывала `setState` прямо в эффекте, на это ругается правило `react-hooks/set-state-in-effect` (React Compiler).

## 2026-09-19 — Защита маршрутов: proxy + requireUser

`src/proxy.ts` (в Next 16 `middleware` переименован в `proxy`) проверяет только наличие cookie сессии и редиректит на `/login?next=…`. Настоящая проверка — `requireUser(roles?)` в `src/server/session.ts`: сессия через Better Auth, роль и `isActive`. Так сделано потому, что proxy выполняется в отдельной среде и не должен ходить в БД (см. `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md`).

Из-под защиты выведены `/login`, `/api/auth/*` и `/api/integrations/*` — у вебхуков сайта своя подпись HMAC.

`requireUser` без сессии делает `redirect("/login")`, при нехватке роли кидает `ForbiddenError` (403 для Server Actions и route handlers). Отдельного экрана 403 пока нет: `forbidden()` в Next 16 под флагом `experimental.authInterrupts`, включать ради заглушек не стали.

## 2026-09-19 — Деактивированный пользователь не входит

Better Auth про `isActive` не знает, поэтому проверка в двух местах: `signInWithPassword` (`src/server/auth-service.ts`) смотрит флаг до вызова `auth.api.signInEmail`, а `getSessionUser` считает сессию деактивированного несуществующей. Сообщение о неверном пароле одно на все случаи — существование учётной записи не раскрываем.

Ограничение попыток входа — встроенный `rateLimit` Better Auth: 10 запросов к `/sign-in/email` за 15 минут. Хранилище — память процесса; считаются все попытки, а не только неудачные (PRD требует «10 неудачных»). Для одного инстанса приемлемо; при нескольких инстансах или при точном соблюдении формулировки нужен свой счётчик в БД. **Пересмотрено 2026-09-20** — счётчик в БД сделан, см. запись «Неудачные входы считаются в БД».

## 2026-09-19 — Первый админ — сид, а не форма регистрации

`prisma/seed.ts` (`pnpm db:seed`, он же `migrations.seed` в `prisma.config.ts`) создаёт ADMIN из `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD` и демо-каталог. Пароль хешируется `hashPassword` из `better-auth/crypto` — той же функцией, что использует Better Auth по умолчанию, и кладётся в `account` с `providerId: "credential"`. Через `auth.api.signUpEmail` нельзя: регистрация выключена (`disableSignUp`). Сид идемпотентен: существующего пользователя не трогает, товары — `upsert`.

## 2026-09-19 — Postgres без Docker на машине разработчика

Docker на машине не установлен, зато стоит нативный PostgreSQL 16 на 5432. Для разработки используем его: роль `buscom` / БД `buscom_erp` с теми же логином и паролем, что в `docker-compose.yml`, чтобы `DATABASE_URL` был одинаковым при любом способе. `docker-compose.yml` оставлен для CI и других машин.

## 2026-09-19 — `account.accountId` для пароля = id пользователя

При входе Better Auth ищет аккаунт условием `providerId === "credential" && accountId === user.id` (`better-auth/dist/api/routes/sign-in.mjs`). Если положить в `accountId` email, пароль не находится и вход отдаёт 401 «Invalid email or password» без внятной причины. В `prisma/seed.ts` пользователь создаётся первым, затем аккаунт с `accountId: user.id`. То же правило — для будущего создания пользователей администратором.

## 2026-09-20 — Сервис заказов: одно действие — одна транзакция

`src/server/orders/` разбит по действиям (`create`, `status`, `assignment`, `items`, `payments`, `comments`), общее — в `internal.ts`. Каждое действие открывает `db.$transaction` и внутри него меняет заказ, остатки и пишет `OrderEvent`: журнал не может разойтись с данными, даже если запрос оборвётся. Итоги всегда пересчитывает `recalculateOrderTotals` из позиций — суммы с клиента не принимаются.

Резерв остатка живёт в двух слоях: `src/domain/order/reservation.ts` решает, что делать при переходе (`RESERVE` / `RELEASE` / `SHIP` / `NONE`), а `src/server/orders/reservation.ts` применяет это к товарам. Правило выведено из одного предиката «статус держит резерв» — так не нужно перечислять все пары переходов.

Защита от одновременной работы: `changeOrderStatus` принимает `expectedStatus` (статус, который видел пользователь) и отклоняет изменение, если его успели сменить; «Взять себе» не перезаписывает чужого менеджера, а объясняет, у кого заказ.

## 2026-09-20 — `ForbiddenError` вынесена из `session.ts`

`session.ts` импортирует `next/navigation` и `next/headers`, поэтому любой сервис, бравший оттуда `ForbiddenError`, переставал работать вне запроса Next — это всплыло на первом же скрипте проверки. Ошибка переехала в `src/server/errors.ts` без зависимостей от Next; `session.ts` реэкспортирует её для совместимости. Правило: значения, нужные сервисам, не держим в модулях, завязанных на Next.

## 2026-09-20 — `paidKopecks` и `slaDueAt` в заказе

Два фильтра из PRD нельзя выразить запросом к нормализованным данным: «статус оплаты» требует суммы платежей, «просроченные» — расчёта рабочих минут. Считать их перебором нельзя: список постраничный и должен держать 100 000 заказов.

Поэтому в `Order` добавлены два поля-кэша. `paidKopecks` — сумма принятых платежей, увеличивается в той же транзакции, что и сам платёж. `slaDueAt` — дедлайн текущего статуса, считается `addWorkingMinutes` при каждой смене статуса. Сам статус оплаты по-прежнему не хранится: его выводит `paymentStatus(totalKopecks, paidKopecks)` — правило осталось в одном месте, изменилась только форма хранения слагаемого.

Риск — расхождение кэша с платежами, если кто-то запишет `Payment` мимо `addPayment`. Правило: платежи только через сервис; при появлении импорта оплат добавить сверку.

## 2026-09-20 — Состояние списка заказов живёт в URL

Вид, фильтры, поиск и страница — параметры адреса, а не состояние React. Список можно переслать коллеге, открыть в новой вкладке и вернуть кнопкой «назад»; серверный компонент читает их из `searchParams`, разбирая схемой в `src/app/(app)/orders/params.ts` — из URL приходит что угодно. Вкладки и пагинация — обычные ссылки, фильтры — клиентский компонент, который переписывает адрес через `router.push`.

## 2026-09-20 — Подпись считается от сырого тела

`POST /api/integrations/site/orders` читает тело как текст (`request.text()`) и проверяет HMAC до разбора JSON. Пересериализация тела ломает подпись: порядок ключей и пробелы у отправителя и получателя различаются. Сравнение — `timingSafeEqual`, разная длина отбрасывается заранее (сама функция на разной длине бросает исключение).

Неподписанный запрос отвергается с 401 и **не пишется** в `IntegrationInbox`: журнал интеграции — для заказов, а не для мусора из интернета.

## 2026-09-20 — Тесты серверного слоя: заглушка `server-only`

Пакет `server-only` намеренно бросает исключение при импорте вне серверной среды Next, поэтому `src/server/**` нельзя было тестировать. В `vitest.config.mts` добавлен алиас на пустой модуль `src/test/server-only-stub.ts`. Это открыло тесты для серверных модулей без БД (подпись вебхука, разбор контракта). Модули, которые ходят в Prisma, всё ещё требуют живого Postgres — он появится в CI отдельной задачей.

## 2026-09-20 — Настройки: умолчания в домене, в БД только изменённое

`Setting` хранит значение по ключу как JSON, `DictionaryItem` — простые списки. Значения по умолчанию заданы в `src/domain/settings.ts` и берутся, пока администратор ничего не менял: пустая база сразу работоспособна, а новые настройки не требуют миграции данных. Негодное значение из БД не роняет систему — `parseSetting` откатывается к умолчанию.

Справочники не удаляются, а гасятся `isActive`: в старых заказах причина отмены хранится текстом, и удаление позиции оставило бы записи без объяснения.

Позиции справочника причин проверяются на сервере при отмене: список, пришедший из формы, доверия не заслуживает.

## 2026-09-20 — Отключение сотрудника удаляет сессии

`setUserActive(false)` в одной транзакции снимает флаг и удаляет строки `session` — PRD требует, чтобы деактивированный терял доступ сразу. То же делает смена пароля. Себя отключить или снять с себя роль ADMIN нельзя: иначе систему можно оставить без администратора.

## 2026-09-20 — PDF через pdfmake со шрифтом из пакета

Счёт и комплектовочный лист собирает `pdfmake`. Кириллица требует встроенного TTF: стандартные шрифты PDF её не содержат. Roboto лежит внутри самого пакета (`node_modules/pdfmake/build/fonts/Roboto`), поэтому бинарный шрифт не попадает в репозиторий и не требует отдельной загрузки при сборке. Наличие кириллических глифов в готовых файлах проверено разбором карты ToUnicode.

Документы отдаёт route handler `/api/orders/[number]/documents/[kind]`, а не Server Action: браузеру нужен файл. `Content-Disposition: inline` — документ открывается во вкладке, откуда его печатают или сохраняют. Доступ к сети и файловой системе у pdfmake отключён, кроме каталога со шрифтами.

Сумма прописью («Двадцать четыре тысячи пятьсот рублей 00 копеек») — отдельный доменный модуль `src/domain/money-words.ts` с тестами: русские правила склонения числительных ошибаются на 11–14 и на женском роде тысяч, а без верной формулировки счёт не принимает бухгалтерия.

## 2026-09-20 — Интеграционные тесты: только по базе со словом «test» в имени

Тесты сервисов живут рядом с кодом как `*.db.test.ts` и идут только при `RUN_DB_TESTS=1`. `resetDb` чистит все таблицы `TRUNCATE`, поэтому стоит вторая проверка: имя базы обязано содержать `test`, иначе функция отказывается работать. Без этих условий блок помечается `describe.skip` — `pnpm test` остаётся зелёным на машине без тестовой базы.

`src/test/setup.ts` подставляет заглушки переменных окружения: `src/server/env.ts` валидирует их при импорте, и файл с тестами падал бы ещё до того, как решится его пропускать.

В CI поднимается сервис `postgres:16-alpine` с базой `buscom_test`, перед тестами выполняется `prisma migrate deploy`. Это заодно проверяет сами миграции на каждом пуше — раньше они применялись только руками.

## 2026-09-20 — Без SMTP письмо не теряется, а пишется в лог

Отправкой писем занимается `src/server/mail.ts` (nodemailer, настройки из env). Если `SMTP_HOST` не задан, письмо не отправляется, а его текст печатается в лог сервера с предупреждением. Так локальная разработка не требует почтового сервера, а в бою незаполненные настройки видно сразу — вместо тихо пропавших писем.

Ответ на запрос сброса одинаков для существующего и несуществующего адреса: иначе по форме можно перебрать список сотрудников. Ссылка живёт час и срабатывает один раз.

## 2026-09-20 — Слияние клиентов переносит данные, а не затирает

`mergeCustomers` переводит заказы и адреса дубля на основного клиента, а пустые поля основного заполняет значениями дубля (телефон, email, ИНН, КПП); комментарии склеиваются. Дубль удаляется физически — в отличие от заказов, история клиента-дубля ценности не имеет, а ссылки на него переехали.

Адрес «по умолчанию» после слияния остаётся один: признак у переносимых адресов снимается, если у основного клиента он уже есть. Первая версия это пропускала — нашлось проверкой на живой БД.

Сумма покупок клиента считается по заказам в статусах SHIPPED и COMPLETED: деньги за незакрытую сделку ещё могут не дойти. В списке она берётся одной группировкой по показанной странице, а не запросом на каждую строку.

## 2026-09-20 — Замер списка на 100 000 заказов

PRD требует от списка заказов ≤ 500 мс (p95). Проверено: 100 000 заказов и 2 000 клиентов засеяны в локальный Postgres, измерены времена ответа production-сборки по HTTP, данные удалены. Результат — с запасом: список 56 мс, вкладки со счётчиками 39–40 мс, фильтры 27 мс, глубокая страница 34 мс (p95).

Узкое место — поиск одним полем: 210 мс по номеру и 284 мс по телефону. Он идёт `OR` по связанному клиенту (телефон, email, ИНН, имя), и одним индексом это не закрывается. Пока в пределах требования; когда упрётся — собирать поисковую строку в отдельное поле заказа и вешать на неё GIN-индекс, а не наращивать OR.

Счётчики пяти вкладок считаются пятью `count` параллельно с выборкой. На 100 000 заказов это не стало проблемой, потому что каждый запрос ложится на индекс (`status`, `managerId`, `slaDueAt`).

## 2026-09-20 — Правка состава пересчитывает резерв на разницу

`updateOrderItems` у заказа, который уже держит резерв (PAID, ASSEMBLY — правит руководитель), меняет `reserved` у товаров на разницу между прежним и новым составом. Первая версия этого не делала, и резерв оставался от старых позиций. Считается именно разница, а не «снять и поставить заново»: так не нужно гонять остаток туда-обратно и меньше шансов разойтись при ошибке в середине.

Пересчёт идёт до подмены позиций — нужен и прежний состав, и новый, в одной транзакции с записью `OrderEvent`.

## 2026-09-20 — Права страницы дают 403, права действия — сообщение

Появилось два хелпера вместо одного. Страницы (`page.tsx`) зовут `requirePageUser(roles)`: при неподходящей роли он вызывает `forbidden()` из `next/navigation`, Next отдаёт настоящий статус 403 и рисует `src/app/(app)/forbidden.tsx`. Экран лежит внутри группы `(app)`, поэтому меню и шапка остаются — человеку видно, куда идти вместо закрытого раздела.

Server Actions и сервисы остались на `requireUser(roles)` с `ForbiddenError`. Поменять их на `forbidden()` нельзя: действия ловят ошибку и показывают текст тостом, а `try/catch` вокруг `forbidden()` глушит интеррапт — экран 403 не отрисуется, и пользователь не увидит ничего.

`forbidden()` экспериментальный, поэтому в `next.config.ts` включён флаг `experimental.authInterrupts`.

Проверено на живой БД временным сотрудником, которому по очереди выдавались все четыре роли: HEAD получает 403 на `/admin/users` и `/admin/dictionaries`, MANAGER — на всём разделе `/admin`, WAREHOUSE — ещё и на `/orders/new`. Статус именно 403, не 200: проверка роли успевает до начала стриминга.

Эта запись отменяет оговорку из «2026-09-19 — Защита маршрутов: proxy + requireUser» о том, что экрана 403 нет, а флаг включать не стали: экраны администрирования перестали быть заглушками, и флаг себя окупил.

## 2026-09-20 — Проверка живости в деплое читала собственный скрипт

Первый выкат отрапортовал успех при полностью нерабочем приложении — то есть страж, поставленный ровно против этого, сам же это и пропустил.

Причина: скрипт деплоя подаётся на сервер через `ssh ... bash -s` по stdin, а внутри стояла проверка `docker compose exec -T app node -e "fetch(...)"`. `exec -T` читает stdin — и съел остаток собственного скрипта. Bash дошёл до конца файла, вышел с нулём, шаг засчитался успешным: ни строки «приложение отвечает», ни сообщения об ошибке в логе.

Проверка переписана на `curl` к опубликованному порту с хоста. Это не только чинит дефект, но и честнее по сути: проверяется тот самый путь, которым ходит проксирование хостинга, а не только внутренности контейнера. Всем командам в удалённом скрипте, которые могут трогать stdin, добавлен `< /dev/null`.

Правило на будущее: в скрипте, который сам приходит по stdin, любая команда, читающая stdin, должна получать `< /dev/null`.

## 2026-09-20 — Неудачные входы считаются в БД, лимитер Better Auth остался защитой от флуда

PRD, M8 требует «10 **неудачных** попыток за 15 мин — блокировка на 15 мин». Встроенный `rateLimit` Better Auth это правило не выражает: он считает все запросы к `/sign-in/email` с одного адреса, не различая верный пароль и неверный, и живёт в памяти процесса — перезапуск контейнера обнуляет счётчик, а один NAT запирает целый офис (запись 2026-09-19 выше это и фиксировала как долг).

Теперь счётчик свой:

- правило — в домене (`src/domain/auth/login-throttle.ts`), чистая функция по меткам времени: 10 неудач в окне 15 минут закрывают вход, разблокировка — когда десятая с конца выходит из окна;
- хранение — таблица `FailedLogin` (миграция `20260920131928_failed_login_attempts`), ключ — email в нижнем регистре, рядом адрес из `X-Forwarded-For` для разбора инцидентов;
- вызовы — в `signInWithPassword`: проверка до пароля, запись после неудачной проверки, очистка при успешном входе. Пока вход заблокирован, попытки **не** пишутся — иначе перебор продлевал бы блокировку сам себе.

Ключ — email, а не адрес: PRD ограничивает подбор пароля к учётной записи, а сотрудники ходят из одной сети. Перебор по многим адресам такой счётчик не ловит, поэтому `rateLimit` Better Auth оставлен, но с заведомо высоким порогом (60 запросов за 15 минут с адреса) — он теперь именно защита от флуда и не срабатывает раньше правила PRD.

Старьё чистится при записи новой неудачи, по всем адресам сразу — отдельный крон ради одной маленькой таблицы не нужен, а перебор по разным email иначе копил бы мусор.

Проверено не только тестами (11 доменных + 8 по живой БД), но и руками в браузере: девять неудач дают обычное «Неверный email или пароль», десятая — «Слишком много неудачных попыток входа. Попробуйте через 15 минут», после чего **верный** пароль тоже отклоняется, а новых строк в журнале не появляется. После истечения окна вход проходит и журнал по этому email обнуляется.

## 2026-09-20 — Выгрузка списка: CSV под Excel, а не XLSX

PRD, M7 просит «выгрузку любого списка в XLSX/CSV». Первым сделан CSV для списка заказов: он не тянет в зависимости библиотеку для XLSX и покрывает то, ради чего выгрузку просят — открыть в Excel, посчитать, отправить.

Формат подобран под Excel с русской локалью (`src/domain/csv.ts`): разделитель — точка с запятой, перевод строки CRLF, BOM в начале файла. С запятой и без BOM Excel открывает файл одной колонкой и ломает кириллицу.

Ячейку, начинающуюся с `=`, `+`, `@` или таба, Excel выполняет как формулу — это известная дыра выгрузок (CSV injection), поэтому такие значения предваряются апострофом. Отрицательное число под правило не попадает. Из-за этого же телефоны в выгрузке пишутся с восьмёрки (`formatPhoneLocal`): с `+7` ячейка выглядела бы формулой, а апостроф перед номером был бы виден в таблице.

Суммы — числами без знака валюты и без разделителя тысяч (`formatRubPlain`), чтобы Excel мог их складывать; статусы, оплата и источник — словами, как в списке на экране.

Выгружается ровно то, что видно на экране: условия выборки строит общая с списком функция `ordersWhere`, различие одно — в файле нет пагинации. Потолок 10 000 строк: файл собирается в памяти одной строкой. Упёрлись — это видно в имени файла (`zakazy-2026-09-20-pervye-10000.csv`) и в заголовке `X-Export-Truncated`; следующим шагом здесь будет отдача потоком по курсору.

## 2026-09-20 — Работа идёт в `development`, выкат — только из `main`

Повседневные коммиты идут в ветку `development`, в `main` её вливает владелец по явной просьбе. Причина простая: пуш в `main` сам по себе выкатывает на боевой сервер, а админкой уже пользуются — момент обновления должен выбирать человек, а не порядок коммитов.

Механика деплоя этому не мешала и раньше: job висит на `workflow_run` от «CI» с фильтром `branches: [main]`, а он смотрит на ветку того самого прогона CI. Прогон по `development` (и по PR из неё) деплой не запускает. Добавлено к этому два уточнения:

- CI теперь запускается и на пуш в `development` — иначе проверки ждали бы PR, а ветка задумана как обычное место для коммитов;
- ручной запуск деплоя (`workflow_dispatch`) разрешён только с `main` или с тега. Без этого условия любой мог бы выбрать `development` в списке веток при запуске вручную и выкатить то, что в `main` ещё не влито. Тег оставлен намеренно — им делается откат на прошлую версию.

Ветка `main` остаётся веткой по умолчанию в GitHub: на неё завязаны `workflow_run` (событие приходит только от workflow из ветки по умолчанию), база для PR и `git reset --hard` в скрипте выката.

## 2026-09-20 — Миграция удаления склада написана руками

`prisma migrate dev` на этих правках сгенерировал бы для enum-ов DROP TYPE + CREATE TYPE, то есть потерю значений: заказы в статусе `ASSEMBLY` остались бы без статуса, а сотрудники с ролью `WAREHOUSE` уронили бы миграцию. Поэтому `20260920170000_warehouse_removed` написана вручную:

- `ALTER TYPE "OrderStatus" RENAME VALUE 'ASSEMBLY' TO 'SHIPPING'` — заказы в этом статусе переезжают сами, данные не трогаем;
- `UserRole` пересоздаётся (переименования значения мало — значение уходит совсем), но перед приведением типа складские сотрудники переводятся в менеджеры: `UPDATE "user" SET "role" = 'MANAGER' WHERE "role" = 'WAREHOUSE'`. Порядок важен — иначе приведение типа падает;
- `DROP COLUMN` у `Product` для четырёх складских полей.

Общее правило на будущее: удаление или переименование значения enum в Postgres — всегда ручная миграция с явным переносом данных, генератору такое доверять нельзя.

## 2026-09-21 — Телефон клиента уникален, email — нет

Импорт базы из прежней ERP нужно уметь прогонять повторно, не плодя дублей, а ключа записи в выгрузке нет ни одного. Ключом сделан телефон: он и так нормализован до `+7XXXXXXXXXX` и уже служит для сопоставления заказов с сайта. `Customer.phone` получил `@unique`, оставшись при этом необязательным — в Postgres UNIQUE допускает сколько угодно NULL, а клиентов без телефона в выгрузке 354.

Email уникальным не делаем: одна почта бухгалтерии на несколько юрлиц — обычное дело, в выгрузке таких 169 строк. Из этого следует правка сопоставления: `findCustomer` берёт клиента по email, только если email ровно у одного. Иначе заказ с общей почты привязался бы к случайному из нескольких.

Побочное следствие — `mergeCustomers` сливает в другом порядке: дубль удаляется до правки основного клиента, иначе перенос номера с ещё живого дубля упирается в уникальный индекс.

## 2026-09-21 — Адрес клиента одной строкой

У `CustomerAddress` был отдельный `city`. Убран: в выгрузке прежней ERP адрес записан одной строкой (2942 значения, города отдельно нет), с сайта он приходит так же, а разбирать чужие строки на части всё равно нечем. Существующие города миграция приклеила к адресу, а не выбросила.

## 2026-09-21 — Реквизиты юрлица в Json, а не колонками

Реквизиты для договоров (юр. название и адрес, ОГРН, банк, БИК, р/с, к/с, руководитель, бухгалтер) легли в `Customer.requisites` — поле типа Json, заведённое под это ещё в начальной схеме. Девять колонок ради 874 клиентов из 4306 не окупаются, фильтров и поиска по ним не планируется, а форма задана Zod-схемой `customerRequisitesSchema` в домене — то есть проверяется на входе, как если бы это были колонки.

Контактное лицо и паспорт — наоборот, обычные колонки: они нужны в карточке у всех, а не только у юрлиц с полными реквизитами.

## 2026-09-21 — Импорт клиентов: скрипт, а не экран

Импорт базы из прежней ERP сделан скриптом `pnpm import:customers`, а не экраном загрузки. Прогон разовый, файл содержит персональные данные (его место — в `misc`, закрытой `.gitignore`), а отчёт удобнее читать в консоли. Экран пришлось бы защищать правами, ограничивать размер файла и держать прогресс — всё это ради одного применения.

Идемпотентность — по ключу строки: телефон, иначе ИНН. Уже заведённого клиента импорт не перетирает, а дозаполняет пустые поля: то, что человек ввёл в ERP, всегда свежее выгрузки. Комментарий дописывается, а не заменяется. У 315 строк ключа нет вовсе — они считаются отдельно, и повторный прогон их задвоит; на этот случай есть `--only-keyed`.

Скрипты запускаются через `tsconfig.scripts.json`, где `server-only` подменён заглушкой: вне Next этот пакет бросает ошибку, а скрипту нужен серверный слой. Тот же приём, что в `vitest.config.mts`.

## 2026-09-21 — Пагинация одна на все списки

Компонент пагинации был только у заказов и вёл на `/orders` жёстко зашитым путём. У клиентов и товаров кнопок страниц не было вовсе — в шапке печаталось «страница 1 из 87», а перейти на вторую можно было только руками через `?page=`. На демо-данных это не бросалось в глаза: пока в базе шесть клиентов, страница одна. Проявилось сразу после импорта 4306 клиентов.

`OrdersPagination` заменён на `ListPagination` в `components/layout/`: те же ссылки, но путь и подпись приходят пропсами. Счётчик «всего» переехал из шапки экрана в сам компонент — чтобы число и кнопки жили в одном месте и не разъезжались.

## 2026-09-21 — `min-w-0` против горизонтального скролла страницы

Широкая таблица распирала не свой контейнер, а страницу целиком: `SidebarInset` — флекс-элемент рядом с меню, а у флекс-элемента `min-width: auto`, то есть ужиматься уже содержимого он отказывается, и `overflow-x-auto` на обёртке таблицы не срабатывал. Добавлен `min-w-0` — ему и обёрткам таблиц в списках. Теперь прокручивается таблица внутри рамки, а страница стоит на месте.

Правка затронула `components/ui/sidebar.tsx` — файл от shadcn. Если он будет перегенерирован, `min-w-0` придётся вернуть.

## 2026-09-21 — Клиент удаляется физически, а заказ — нет

Заказы по PRD не удаляются физически, только `deletedAt`. Для клиента решено иначе — обычный `DELETE`:

- у клиента без заказов терять нечего: история сделок живёт в заказах, а их у него нет;
- телефон клиента уникален. Помеченная удалённой запись навсегда заняла бы номер, и завести человека заново стало бы нельзя — а именно это и нужно, когда чистят мусор из импорта («1», «02052025» и подобное);
- `deletedAt` пришлось бы дописать в каждый запрос: список, поиск, подбор при создании заказа, сопоставление по телефону, выгрузка. Забытый фильтр в любом из них — тихий баг.

Клиента с заказами удалить нельзя: заказ ссылается на него обязательным полем, и без клиента карточка заказа осталась бы без покупателя. Проверка считает и удалённые заказы — строки в базе они занимают, внешний ключ их держит. Такой дубль объединяют с основным клиентом (`mergeCustomers`), заказы переезжают туда.

Право на удаление уже, чем на правку: `CUSTOMER_DELETE_ROLES` — только HEAD и ADMIN. Основание — PRD, где менеджеру не положено удалять заказы; удаление клиента ничуть не безобиднее. Если менеджерам это понадобится, правка в одну строку в `src/domain/user/role.ts`.

## 2026-09-21 — Архивные заказы: своё значение источника, а не OTHER

Импортированным заказам дан источник `LEGACY` («Прежняя ERP»). Отдельное значение, а не `OTHER`: архивных заказов 3017 против полутора десятков рабочих, и без своего источника их не отделить в списке от заказов «прочее». Добавление значения в enum данные не трогает.

Попутно список источников свёлся к одному месту: он был продублирован в четырёх (`ORDER_SOURCE_LABELS`, схема разбора параметров, фильтр списка, форма нового заказа), и `LEGACY` пришлось бы дописывать в каждое. Теперь `ORDER_SOURCES` и `ORDER_CREATE_SOURCES` считаются из подписей. `LEGACY` в форму заведения заказа не попадает намеренно: его ставит только импорт.

## 2026-09-21 — У архивного заказа одна позиция на всю сумму

В выгрузке прежней ERP позиций нет — есть строка «Описание» (в среднем 62 символа) и общая сумма. Итог заказа у нас считает сервер из позиций, поэтому заказ без позиций показывал бы «Товары 0 ₽» при итоге в 20 000 ₽ — в карточке это выглядит как ошибка расчёта, а не как особенность архива.

Решение: одна позиция с артикулом `ИМПОРТ`, количеством 1 и ценой во всю сумму заказа. По артикулу такие строки видно и в карточке, и в выгрузке. Разносить цену по перечислению из «Описания» через запятую не стали — честных цен в источнике нет, и любое деление было бы выдумкой.

## 2026-09-21 — Архив занимает номера 1..N, рабочие заказы сдвигаются

Номер заказа в прежней ERP не уникален: 1892 разных номера на 3017 строк, повторы за разные годы. Сохранить их как есть нельзя — `Order.number` уникален.

По решению владельца архив занял начало последовательности: заказы 1..3017 по дате, самый старый — первый. Заказы, заведённые в этой системе, скрипт сдвигает выше архива и двигает саму последовательность, чтобы следующий заказ не столкнулся с архивом. Сдвиг идёт в два прохода через отрицательные номера: прямой `UPDATE` налетел бы на собственный уникальный индекс.

Сдвиг рабочих заказов — вещь заметная (номер заказа печатается в счёте), поэтому он требует явного `--renumber`. Без флага скрипт отказывается и говорит, сколько заказов мешает.

Статус у всех перенесённых — «Выполнен». Это архив, вести его никто не будет, а в незакрытых статусах он засорял бы вкладки и «Просроченные». Номер в прежней ERP, кто оформил, её статус отправки и выделенный НДС уходят в запись журнала: полям заказа они не соответствуют, но теряться не должны.

## 2026-09-21 — Поставщики: цепочка этапов — подстатусы «в работе», а не замена статусов заказа

Владелец попросил раздел «Поставщики» с цепочкой статусов, по которой строится флоу заказа с их товарами. Решение (согласовано с владельцем): **глобальный статус заказа остаётся главным и прежним** (`src/domain/order/status.ts` не потерял ни одного перехода), а этапы поставщика — его подстатусы, пока заказ в работе. В заказе с товарами нескольких поставщиков у каждого свой трек (`OrderSupplierTrack`), они двигаются независимо.

Что из этого следует:

- **Где двигаются этапы.** Владелец назвал это «подстатусами для В работе». Буквально только `IN_PROGRESS` не подходит: при предоплате заказ уходит в «Ждёт оплаты» и «Оплачен», а поставщику часто платят как раз после оплаты клиента — трек замёрз бы на полпути. Поэтому «в работе» — это `SUPPLIER_WORK_STATUSES`: `IN_PROGRESS`, `AWAITING_PAYMENT`, `PAID`. Если владелец захочет строже — правка одной константы.
- **Где цепочка влияет на заказ.** Переход в `SHIPPING` (и из «Оплачен», и постоплатой из «В работе») проверяет `assertTransition`: все треки должны стоять на последнем этапе. Проверка живёт в домене вместе с остальными правилами переходов, сервер передаёт туда положение треков. Отмену треки не держат.
- **Порядок этапов** — шаг вперёд или шаг назад (исправить ошибку). Перепрыгивать нельзя, иначе цепочка перестаёт означать последовательность.
- **Этап хранится ссылкой, а не индексом.** Переименование и перестановка этапов не сдвигают заказы; этап, на котором стоит хоть один трек, удалить нельзя (`onDelete: Restrict` + понятная ошибка в сервисе).
- **Треки повторяют состав заказа**: появился поставщик в позициях — трек «не начат», ушёл — трек удаляется (с прогрессом; смена состава и так пишется в журнал).
- **Цена у поставщика — закупочная** (`ProductSupplier.purchasePriceKopecks`), цена продажи остаётся в товаре. Позиция заказа хранит снимок закупки, как и снимок цены продажи; сервер берёт её из привязки, а при пересохранении состава сохраняет прежний снимок для той же пары товар–поставщик — иначе правка количества молча переписала бы закупку по новому прайсу.
- **Поставщик в позиции выбирается только из поставщиков товара**: иначе закупочную цену взять неоткуда. У произвольной позиции поставщика нет.
- **Удаление поставщика** физическое, как у клиента, и запрещено, если он есть в позициях или треках заказов (в том числе удалённых).
- Тип «физлицо / юрлицо» переиспользует enum `CustomerType`, а реквизиты — форму `CustomerRequisites`: поля те же, заводить параллельные сущности незачем.

## 2026-09-21 — Источники заказов — справочник, enum `OrderSource` остался техническим каналом

Владелец попросил список источников в настройках, редактируемый (добавить «Авито», «Выставку», переименовать, выключить), и смену источника в карточке заказа.

Enum `OrderSource` не выброшен: на нём держится идемпотентность интеграции и импорта — уникальный ключ `(source, externalId)`. Поэтому источников у заказа два уровня:

- `Order.source` — технический канал. `SITE` ставит интеграция, `LEGACY` — импорт; заказы, заведённые руками после этой правки, получают `OTHER`;
- `Order.sourceItemId` → `DictionaryItem` типа `ORDER_SOURCE` — то, что видит и выбирает человек: список, фильтр, выгрузка, карточка, форма.

Пункты «Сайт» и «Прежняя ERP» — системные (`DictionaryItem.systemCode`): их можно переименовать, но нельзя выключить и нельзя выбрать руками. Иначе заказ, заведённый менеджером, выдавал бы себя за пришедший с сайта. По той же причине у заказов с сайта и из прежней ERP источник в карточке не меняется.

Миграции две: `20260921180000_order_sources` добавляет значение enum и колонки, `…_backfill` заводит шесть пунктов из прежнего фиксированного списка и привязывает к ним все существующие заказы. Разделены потому, что Postgres не даёт использовать новое значение enum в той же транзакции, где его добавили. Если справочник пуст (чистая тестовая база), системный пункт заводится сам — `resolveSystemSource`.

Подпись без пункта справочника — запасная по каналу (`orderSourceLabel`): так ведут себя заказы, созданные в тестах напрямую, и так не сломается ничего, если пункт когда-нибудь не найдётся.

## 2026-09-21 — Каталог с сайта: обход страниц, а не выгрузка из админки OpenCart

Доступа к админке и базе сайта нет, YML-выгрузки (`yml.xml`) тоже — отдаёт 404. Поэтому товары берутся с публичных страниц: список — из `sitemap.xml`, карточка — из отладочного JSON, который тема сайта печатает в `console.log` (там `product_id`, `model`, цена, статус), с запасным разбором разметки на случай, если отладку уберут. Категорий в карточке нет — они сопоставляются по ссылкам из листингов категорий меню.

Обход и импорт разделены: `fetch:site-products` пишет JSON, `import:site-products` читает его. Сайт открывается не отовсюду (VPN), а импорт по готовому файлу можно повторять и проверять `--dry-run`. Когда появится интеграция с сайтом (этап 2), этот путь заменит синхронизация каталога, но ключ останется тем же — `Product.externalId` = `product_id`.

Повторяющиеся на сайте артикулы получают суффикс `-<product_id>` у всех, кроме первого: в ERP артикул уникален, а выбрать «правильный» дубль автоматически нельзя. Суффикс однозначен и воспроизводим при каждом прогоне.

## 2026-09-21 — Опции товара: группы с надбавкой, в заказе — снимок выбора

На сайте у 60 товаров опции в стандартном виде OpenCart: группа («Ремень», «Выбор стекла Ford Transit LWB») и варианты с надбавкой к цене («Трехточечный +1 750 руб.»). Сценариев два: конфигуратор (сиденье с базовой ценой и доплатами за опору, ремень, подлокотник) и выбор детали (у стёкол и обшивки цена товара 0, цену целиком даёт вариант). Сначала обсуждался вариант разложить каждую опцию «нулевых» товаров в отдельный товар — владелец выбрал опции внутри ERP: так покрываются оба сценария и не плодятся сотни почти одинаковых карточек.

Модель: `ProductOption` (группа, `required`) → `ProductOptionValue` (название, `priceDeltaKopecks`). В позиции заказа — не ключ варианта, а снимок `OrderItem.options` (Json: группа, вариант, надбавка, id варианта), по тому же правилу, что снимок названия и цены: правка и удаление опций в каталоге старые заказы и счета не меняют.

- **Снимок собирает сервер** (`resolveItemOptions`) из каталога по id вариантов; названия и надбавки с клиента не принимаются. В группе — не больше одного варианта, обязательная группа — ровно один (`buildOptionSnapshot`).
- **Цена позиции** по умолчанию — базовая плюс надбавки, считается в форме при добавлении. Менеджер может поправить её руками, как любую цену позиции: сервер цену позиции не пересчитывает — это было бы запретом на ручную цену, которой пользуются.
- **Пересохранение состава** держит прежний снимок для той же пары товар + набор вариантов, даже если варианты в каталоге уже удалены, — как и снимок закупочной цены.
- **Опции в счёте** печатаются в скобках после наименования: покупатель видит, что оплачивает.
- **Импорт с сайта** переносит группы и варианты с их id на сайте (`externalId`) и при повторном прогоне правит их на месте; опции, заведённые в ERP руками у товара с сайта, заменяются — источник правды для таких товаров сайт. Текстовые опции сайта («Номер цвета», «Установка количества», 7 товаров) не переносятся: это свободный ввод без цены, его место — комментарий к позиции или заказу.
- **Выбор при добавлении**: по умолчанию в группе стоит вариант без надбавки («Нет»), если он есть, — сиденье «как есть» добавляется одним кликом. Поменять опции у уже добавленной позиции нельзя — её удаляют и добавляют заново; если это станет неудобно, это следующий шаг.

## 2026-09-21 — Статусная модель упрощена до четырёх статусов

Решение владельца: глобальных статусов четыре — «Создан» (`NEW`), «В работе», «Выполнен», «Отменён». Промежуточные этапы (счёт, оплата поставщику, отправка) ведутся в цепочках поставщиков — они и есть подстатусы «В работе». Отменяет часть записи «Поставщики: цепочка этапов — подстатусы…»: этапы теперь двигаются только в `IN_PROGRESS`, а держат они переход в «Выполнен», а не в «Отправку».

Что сохранено из прежних правил, но перенесено со статусов на сумму платежей (`paidKopecks`):

- отмена заказа, по которому есть оплата, — только HEAD/ADMIN (раньше: отмена из «Оплачен» и «Отправки»);
- состав после первой оплаты правит только HEAD/ADMIN (раньше: после «Ждёт оплаты»).

Что ушло: автопереход в «Оплачен» при полной оплате — статуса нет, степень оплаты видна бейджем; `isFullyPaid` удалена. Трек-номер для доставки ТК теперь требуется при переводе в «Выполнен» (раньше — в «Отгружен»); `shippedAt` ставится при закрытии заказа. «Куплено на» у клиента — только выполненные заказы.

Миграция `20260921220000_order_statuses_simplified` написана руками, как и миграция склада: значение enum в Postgres не удаляется, тип пересоздаётся. Заказы переведены: «Ждёт оплаты», «Оплачен», «Отправка» → «В работе»; «Отгружен» → «Выполнен» (работа по заказу закончена). Записи журнала с прежними статусами не потеряны: прежний переход дописан текстом в комментарий («Статус до упрощения модели: Оплачен → Отправка»), а поля статусов приведены к новой модели. Нормативы SLA убранных статусов удалены из настройки, иначе она перестала бы читаться.

## 2026-09-22 — Картинки товара: хранение множественное, показ — одна аватарка, файлы в базе

Владелец попросил картинки товаров с сайта; на первом шаге — одна «аватарка», но с заделом под несколько. Модель `ProductImage` (товар → много картинок, порядок `sortOrder`); аватарка — первая по порядку. Галерея позже добавится экраном, без миграции.

**Где лежат файлы — в базе (`bytea`)**, полный размер и превью. Сервер один и маленький, объектного хранилища нет; том на диске пришлось бы отдельно бэкапить и переносить, а база уже бэкапится и переносится (так бой и наполнялся). Объём скромный: 215 аватарок — 39 МБ полных и 3,6 МБ превью. Ссылаться на bus-com.ru напрямую нельзя: у части сотрудников сайт закрыт VPN, а адреса кеша OpenCart меняются. Если картинок станет на порядки больше — переносить в объектное хранилище, модель при этом не меняется (данные → ключ файла).

- **Отдача** — `GET /api/product-images/[id]` (`?size=thumb` — превью) за авторизацией. Замена картинки создаёт новую запись с новым id, поэтому ответ по id неизменен и кешируется браузером на год (`immutable`).
- **Тип файла определяется по сигнатуре**, а не по расширению или `Content-Type`: JPEG, PNG, WebP, GIF, до 5 МБ. SVG не принимается (в нём бывает скрипт), отдаём с `nosniff`. Для загрузки поднят лимит тела Server Action до 6 МБ (`next.config.ts`).
- **Превью** есть у картинок с сайта — OpenCart отдаёт готовое 228×228. У загруженных руками превью нет — в списках показывается полная. Библиотеку ресайза (sharp) ради этого не тянули.
- **Импорт с сайта** (`pnpm import:site-images`) качает главную картинку и превью; ключ повторного прогона — адрес картинки (`sourceUrl`). Сменилась на сайте — аватарка заменяется; загруженную в ERP руками у товара с сайта импорт тоже заменит. Разбор страницы уже собирает и дополнительные картинки (`images` в `site-products.json`) — пригодится для галереи.
- Байты картинок в списки не выбираются: список товаров берёт только id аватарки.

## 2026-09-22 — Справочник категорий товаров с вложенностью

Категория была свободной строкой у товара: новую заводили опечаткой, переименовать разом было нельзя, раздел сайта («Климат» над «Люками») терялся. Теперь справочник `ProductCategory` — дерево (`parentId`), у товара ссылка `categoryId`. Экран — `/products/categories` (ссылка «Категории» в списке товаров): раздел, подкатегория, переименование, перенос в другой раздел, удаление.

- **Глубина** ограничена `CATEGORY_MAX_DEPTH = 4` (на сайте два уровня). Это же позволяет фильтру «по разделу вместе с подкатегориями» обойтись цепочкой `parent.parent…` в одном запросе Prisma, без рекурсивного SQL.
- **Удаляется только пустая категория** — без товаров и подкатегорий (`onDelete: Restrict` у обеих связей плюс понятная ошибка в сервисе). Иначе товары тихо остались бы без категории.
- **Перенос** проверяется на цикл (нельзя внутрь себя и своих потомков) и глубину с учётом собственных подкатегорий; повтор названия запрещён только у соседей — «Люки» могут быть в двух разных разделах.
- **Миграция `20260922120000_product_categories` написана руками**: сгенерированная удалила бы текстовую колонку до переноса. Каждое прежнее название стало категорией верхнего уровня, товары привязаны.
- **Импорт с сайта** передаёт путь `categoryPath: ["Климат", "Люки"]` и раскладывает дерево (`resolveCategoryPath`): уровни ищутся без учёта регистра, недостающие заводятся, а категория верхнего уровня с тем же названием, что у подкатегории, **переносится под раздел, а не дублируется** — так дерево достроилось поверх результата миграции, с сохранением id и товаров. Защита от цикла, если раздел и подкатегория названы одинаково. Старые выгрузки с одной строкой `category` читаются как путь из одного уровня.

## 2026-09-21 — Общая dev-база — вторая база в боевом Postgres

Разработка идёт с двух машин, у каждой была своя локальная база. Состояния расходились: на одной машине заказ есть, на другой нет, миграции накатываются дважды и не в том же порядке. Сделали одну общую базу `buscom_erp_dev` на сервере. Как ей пользоваться — `docs/DEV-DB.md`.

Рассматривались и отклонены: отдельный дешёвый VPS в РФ (изоляция лучше всего, но это деньги и ещё одна машина в обслуживании), отдельный контейнер Postgres на том же сервере (+150–200 МБ памяти там, где свободно ~1 ГБ), Neon/Supabase (бесплатно и удобно, но серверы за рубежом — реальные ПДн клиентов туда нельзя по PRD, а обезличивать дороже, чем вся остальная затея).

Выбрана **вторая база в том же экземпляре Postgres**: 0 ₽, общий процесс не требует лишней памяти, данные остаются в РФ.

- **Изоляция — правами, а не сервером.** Роль `buscom_dev` владеет только своей базой, а с боевой снято `CONNECT` у `PUBLIC` — по умолчанию подключиться к чужой базе может кто угодно, и без этого шага разделение было бы бумажным. Проверено живой попыткой входа: `permission denied for database "buscom_erp"`.
- **Порт опубликован на `127.0.0.1` сервера, внутрь — SSH-туннель** (`pnpm db:tunnel`, локальный порт 5433). Белый список IP не годится: у машин разработки адреса меняются. Адрес `127.0.0.1` в публикации обязателен — без него Docker прописывает правило в iptables в обход `ufw` и база оказывается открыта наружу.
- **Цена решения:** ядро и память сервера общие, поэтому тяжёлый импорт по dev-базе отнимает ресурсы у живой ERP; локальная база оставлена запасным путём для таких прогонов. И `migrate reset` теперь стирает работу обеих машин, а не свою.
- **Тесты остались локальными.** Защита из `src/test/db.ts` (чистить можно только базу со словом `test` в имени) прикрывает общую базу бесплатно: `buscom_erp_dev` под неё не подходит.
- **Бэкапов у dev-базы нет** — `scripts/backup-db.sh` выгружает только боевую. Это рабочее состояние разработки, а не данные компании.

## 2026-09-22 — Фильтры списка заказов запоминаются в cookie, подставляет их сервер

Владелец попросил, чтобы выбранные фильтры сохранялись. Состояние списка по-прежнему живёт в адресе (запись от 2026-09-20 в силе), добавилась только память.

- **Cookie, а не `localStorage`.** Первая версия хранила набор в `localStorage` и подставляла его эффектом через `router.replace`. Владелец сразу заметил мигание: список успевал отрисоваться без фильтров и только потом перерисовывался с ними. Теперь набор лежит в cookie, а серверный компонент `/orders` при пустых параметрах отвечает редиректом — браузер страницы без фильтров вообще не получает. Проверено по логу: `GET /orders 307` и следом `GET /orders?status=… 200`.
- **Cookie приходит снаружи, поэтому разбирается белым списком** (`saved-filters.ts`, 8 тестов): чужие ключи выбрасываются, длина ограничена. Строка идёт в редирект, и подставлять в него что попало нельзя.

- **Номер страницы не запоминается.** Вернуться к фильтрам нужно, к седьмой странице недельной давности — нет.

Попутно выяснилось про первую версию: писать память из `useEffect` по `useSearchParams` нельзя — на первом клиентском рендере хук отдаёт пустые параметры, и отфильтрованный список выглядит как голый `/orders`.

## 2026-09-22 — Поиск клиента по кириллице без учёта регистра: обход, не починка базы

Владелец сообщил, что поиск клиента не находит «БАСКОМ» по запросу «баском». Расследование прямым запросом к dev-базе нашло причину — она серьёзнее одного поля поиска.

- **Корень: база `buscom_erp_dev` создана с кодировкой `SQL_ASCII` и локалью `C`** (`SELECT datcollate, datctype, pg_encoding_to_char(encoding) FROM pg_database` — `C`, `C`, `SQL_ASCII`). При такой кодировке Postgres не проверяет и не интерпретирует байты текста как Unicode вообще — кириллица хранится и отдаётся как есть только потому, что клиент и приложение всегда трактуют её как UTF‑8, но сам Postgres об этом не знает. Отсюда `lower('БАСКОМ')` возвращает «БАСКОМ» без изменений, `'БАСКОМ' ILIKE '%баском%'` — `false`, и ни один ICU collation недоступен («collation for encoding SQL_ASCII does not exist») — само расширение регистронезависимого поиска на эту базу не ставится.
- **Настоящая починка — пересоздать базу с `ENCODING UTF8 LOCALE ru_RU.UTF-8` (или `en_US.UTF-8`)**: `pg_dump` → новая база с нужными параметрами → `pg_restore`. Это простой на время переноса и, вероятно, затрагивает и боевую базу (создавались одним и тем же способом — не проверялось напрямую, боевая база недоступна из среды разработки). Не сделано сейчас: требует окна на боевом контуре и решения владельца, агент базу пересоздавать сам не стал.
- **Пока база как есть — регистронезависимый поиск по имени сделан в приложении**, не в SQL: `matchNamesCaseInsensitive` (`src/server/customers/name-match.ts`) тянет `id, name` всех клиентов и сравнивает через `.toLowerCase()` в JS — тот корректно сворачивает регистр кириллицы независимо от базы. Используется в `lookupCustomers` (подбор при заказе, слияние дублей) и `customersWhere` (список `/customers`, CSV-экспорт), только когда в запросе есть буквы — чистые телефон/ИНН это не трогает.
- **Компромисс сознательный, не спрятанный.** При ~4300 клиентах полный перебор имён на каждый запрос — доли секунды, полноценный SQL-индекс под `contains` всё равно не помог бы (это не prefix-поиск). Если клиентов станет на порядок больше и это станет заметно, дешевле завести колонку `nameLower` (поддерживать при create/update, с индексом), чем чинить локаль всей базы ради одного поля — но по-хорошему разумнее сразу пересоздать базу с правильной кодировкой, раз проблема системная, а не только в этом запросе.
- **Не проверялось, есть ли та же проблема в других местах** (поиск по названию товара, поставщика и т.п.) — чинили только то, о чём сказал владелец. Стоит иметь в виду при следующих жалобах на «не находит».

## 2026-09-22 — «Действия и артефакты» у поставщика: реестр в коде, не в настройках

Владелец попросил раздел в карточке поставщика с чекбоксами — какие функции у него включены, у каждой описание, и чтобы «Заказ поставщику» стала первой такой опциональной функцией. Добавлена и вторая: «Прикрепить счёт поставщика клиенту» — загрузчик файла.

- **Список функций фиксирован в коде** (`src/domain/supplier/actions.ts`), не как отдельный справочник в `/admin/dictionaries`: у каждой функции свой тип UI (кнопка или загрузчик) и своя логика на сервере — заводить произвольную функцию через администратора всё равно было бы нельзя, а добавление новой и так требует кода.
- **У поставщика — `enabledActions: String[]`**, список ключей из реестра. Хранить булевыми колонками на каждую функцию не стали: список будет расти, а миграция под каждую новую функцию — лишняя работа.
- **`enabledActions` по умолчанию — `["SUPPLIER_REQUEST"]`**, и это касается не только новых поставщиков: значение по умолчанию в колонке (`@default(["SUPPLIER_REQUEST"])`) действует и при заливке `ADD COLUMN` на уже существующие строки — «Заказ поставщику» была обязательной функцией, и без этого умолчания все заведённые поставщики потеряли бы кнопку, которая у них и так работала.
- **Неизвестные ключи отбрасываются молча** (`normalizeEnabledActions`) — если функцию когда-нибудь уберут из реестра, у поставщика просто останется списком на один пункт короче, а не сломанное состояние.
- **Прикреплённый файл (`OrderSupplierDocument`) — отдельная модель, не поле в `OrderSupplierTrack`.** Трек поставщика в заказе удаляется, когда позиций этого поставщика в заказе не осталось (`syncSupplierTracks`) — если бы файл лежал в треке, он пропадал бы вместе с ним при правке состава заказа. Уникальность — тройка (заказ, поставщик, вид артефакта): у одной пары заказ–поставщик один активный файл каждого вида.
- **Хранение — как у картинки товара**: байты в базе (`Bytes`), не файловая система и не S3 — бэкапы и перенос в бой идут тем же путём, что и остальные данные. Замена файла — новая запись с новым id вместо правки старой: адрес меняется вместе с содержимым, значит его можно кешировать в браузере навсегда (тот же приём, что у `ProductImage`).
- **Тип файла — по сигнатуре**, не по расширению или Content-Type из формы (тот же принцип, что у картинок товара): PDF или фото счёта (JPEG/PNG/WebP), до 15 МБ.
- **Права — по статусу заказа, не по роли**: прикреплять и убирать файл может любая из трёх ролей (`MANAGER`/`HEAD`/`ADMIN` — других в системе и нет), но не в финальном статусе заказа (`COMPLETED`/`CANCELLED`). Каждое прикрепление, замена и удаление пишут `OrderEvent` (`SUPPLIER_DOCUMENT_CHANGED`) — как и остальные изменения заказа.
- **Миграция создана в обход shadow-базы**: роль `buscom_dev` (и локальная тоже) не имеет `CREATEDB`, а `prisma migrate dev` без него не работает (`P3014`). Использован `prisma migrate diff --from-config-datasource ... --to-schema ... --script` (не требует shadow-базы, сравнивает схему прямо с живой базой) с миграцией, применённой затем через `prisma migrate deploy`.

## 2026-09-23 — «Экономика цены»: формула шагами в JSON поставщика, снимок в заказе

Владелец попросил конструктор конечной стоимости закупки: номинал поставщика плюс комиссии. Ответы на уточнения: нужны проценты, суммы за штуку, суммы за заказ и округление; база процента выбирается у каждого шага; формула одна на поставщика; стоимость видна в поставщике, товарах, заказе и через маржу.

- **Проценты — в сотых долях (550 = 5,5%), суммы — в копейках**, как все деньги в системе. Процент округляется до копейки на своём шаге (половина — вверх), чтобы расшифровка по шагам складывалась ровно в итог.
- **Расходы на заказ — отдельный блок, а не шаг цепочки.** В цену штуки их не выразить без знания количества, а проценты «поверх» них владелец не просил. Снимок — `OrderSupplierTrack.orderCostKopecks` при появлении поставщика в заказе: трек уже живёт ровно столько, сколько поставщик в заказе.
- **Снимок стоимости за штуку — `OrderItem.purchaseCostKopecks`, рядом с номиналом `purchasePriceKopecks`**, и живёт по тем же правилам: пересохранение состава с той же парой товар–поставщик оставляет прежний снимок. Иначе правка формулы задним числом меняла бы маржу закрытых заказов. Миграция заполнила снимок номиналом у всех уже выбранных поставщиков — формул тогда не было.
- ~~**«Заказ поставщику» показывает номинал**, не стоимость для нас~~ — пересмотрено 24.09.2026 по просьбе владельца: в тексте цены с конечной стоимостью, включая экономику цены (снимок `OrderItem.purchaseCostKopecks`; у позиции без снимка — номинал). Расходы на заказ (снимок `OrderSupplierTrack.orderCostKopecks`) — отдельной строкой перед «Итого» и входят в него.
- **«Заказ поставщику (наши цены)» — отдельное действие, а не переключатель в диалоге** (24.09.2026): включается у конкретного поставщика, кому нужно показывать нашу цену. Цена — продажная за штуку из снимка позиции (`OrderItem.priceKopecks`); скидка на позицию не вычитается — она задана на строку целиком и в цену штуки без дробей не делится. Расходов на заказ в этом тексте нет: это закупочная статья.
- **Маржа не считается, если у позиции нет поставщика.** Частичная цифра без части затрат была бы завышенной; честнее сказать, сколько позиций мешают. Доставка клиенту в маржу не входит — она транзитная.

## 2026-09-23 — «Комиссия с прибыли»: процент у поставщика, расчёт в марже заказа

Часть поставщиков удерживает процент от нашей прибыли. Ответы владельца: база — продажа минус стоимость для нас; только процент (без минимумов, максимумов и ступеней); прибыль — по всем товарам поставщика в заказе; скидка на заказ уменьшает её пропорционально.

- **Хранится одним числом** — `Supplier.profitCommissionHundredths` (сотые доли процента, 0 — не удерживает), без JSON: конструктора здесь нет, есть только процент. Понадобятся ступени или минимумы — тогда перевести на формулу, как у «Экономики цены».
- **Снимок — `OrderSupplierTrack.profitCommissionHundredths`**, при появлении поставщика в заказе, рядом со снимком расходов на заказ и по тем же правилам.
- **Сумма комиссии не хранится, а считается** в `calculateOrderMargin` (`src/domain/order/margin.ts`) из снимков: она зависит от цен, скидок и состава, которые меняются до закрытия заказа, и хранимая сумма разъезжалась бы с ними. Прибыль поставщика — его товары со скидками на позиции, минус доля скидки на заказ (`discountShare`, пропорционально сумме товаров, до копейки), минус закупка для нас, минус его расходы на заказ. Комиссия — только с положительной прибыли.
- Расходы на заказ из «Экономики цены» уменьшают базу: это тоже затраты на товары поставщика, и владелец выбрал базу «продажа минус стоимость для нас».

## 2026-09-23 — Посчитанные системой суммы — до целых рублей, половина — в нашу пользу

По просьбе владельца («всегда округляй копейки»): всё, что система вычисляет делением — надбавка по проценту в «Экономике цены», комиссия с прибыли, доля скидки на заказ, — округляется до целых рублей (`src/domain/money.ts`). Сначала половину округляли в большую сторону, но так комиссия 160,5 → 161 уменьшала маржу 374,5 → 374; владелец выбрал вариант «в нашу пользу». Поэтому половина идёт туда, где маржа выше: надбавка к закупке и комиссия — вниз (`roundToRublesHalfDown`: 16,5 → 16, 160,5 → 160; скидка поставщика −12,5 → −13), доля скидки на заказ — вверх (`roundToRubles`: большая доля уменьшает базу комиссии). Хранение по-прежнему в копейках, суммы, введённые руками (цены, номиналы, скидки), не округляются. Уже сохранённые снимки стоимости для нас в заказах не пересчитываются; комиссия и доля скидки считаются на лету и округляются сразу.

## 2026-09-23 — «Подтянуть цену» по варианту товара на vanproject.ru

У части товаров «Фургон Проект» цена зависит от выпадающих списков на странице (стекло: «Расположение» и зависящая от него «Комплектация»). Цена в разметке — цена первого варианта; прежний разбор молча брал её, то есть давал неверную закупку.

- **Списки и зависимости берём из формы товара** (`parseVanprojectForm`, `src/domain/product/vanproject.ts`): `<select name="options[…]">`, подпись из `<span class="prop">`, зависимости из `data-relations` (оно на сайте кривое — не JSON, разбираем пары `ключ=значение`).
- **Цену варианта спрашиваем у сайта тем же запросом, что и браузер** при смене списка: `modification/get` к `action.php` плагина msOptionsPrice (multipart: `id`, `count`, `options[…]`, `action`, `ctx`). Считать цену самим не из чего — модификаций в разметке нет. Проверено вживую: «заднее / 1845х780мм» — 9 250 ₽, «сдвижной двери / с форточкой» — 13 200 ₽.
- **Несуществующее сочетание сайт не отвергает**, а отвечает базовой ценой с `modification.id = 0` — такую цену не берём (`parseModificationPrice`), иначе вернулась бы та же ошибка с первым вариантом.
- **Выбор хранится в паре товар–поставщик** — `ProductSupplier.variant` (JSON `{ ключ: значение }`), только вместе со ссылкой: при смене ссылки в форме выбор сбрасывается. Следующее «Подтянуть цену» сразу спрашивает цену этого варианта.
- В карточке товара: страница с вариантами вместо цены возвращает списки; когда в каждом выбрано значение, цена подтягивается сама. Товары без вариантов — как раньше, цена со страницы.
- curl из Git Bash на Windows получал на этот запрос 401 — портит кириллицу в аргументах; из Node (`fetch`, как на сервере) запрос проходит при любых заголовках.

## 2026-09-23 — Закупка вариантов опций у поставщика и «Подтянуть цены опций»

У товаров вида «Стекла на Citroen Jumper L2» цена продажи целиком в вариантах опций (цена товара 0, варианты — 6 500…14 250 ₽), а поставщик продаёт каждое стекло своим вариантом на странице. Владелец выбрал: закупку хранить отдельно от цены продажи, неоднозначные совпадения — выбирать руками из кандидатов.

- **Таблица `ProductSupplierOptionPrice`** — закупка варианта опции у поставщика (пара товар–поставщик × вариант) и сопоставленный вариант на сайте. Каскадом уходит и с парой, и с вариантом.
- **Закупка позиции в заказе = базовая закупка пары + закупки выбранных вариантов** (`purchaseWithOptions`) — зеркально цене продажи (цена товара + надбавки). Вариант без своей закупки ничего не добавляет. Дальше — как всегда: «Экономика цены», снимок в позиции, маржа. Снимок теперь различает набор вариантов: у той же пары товар–поставщик с другим вариантом — новая закупка.
- **Из формы закупки опций приходят по названиям группы и варианта**, а не по id: у вариантов, добавленных в той же правке, id ещё нет. Названия уникальны без учёта регистра (`normalizeOptionGroups`), сервер пишет закупки после опций. В форме закупка привязана к ключу строки варианта — переименование до сохранения её не теряет.
- **«Подтянуть цены опций»** (`fetchSupplierCombos`) перебирает все допустимые сочетания списков на странице (с учётом зависимостей) и спрашивает цену каждого тем же запросом, что и для одного варианта, по 4 одновременно; больше 80 сочетаний не обходим. Сопоставление (`matchOptionValue`, `src/domain/product/option-matching.ts`): размер обязателен и должен совпасть («1406x667» = «1406х667мм»), сторона — если она есть у поставщика, форточка — есть/нет. Однозначное — сразу в цену, несколько — кандидаты с ценами, ничего — «не найдено». Без размера в названии не угадываем.
- Проверено на ST101 и странице Ducato L2: из 10 вариантов 3 подобрались однозначно (14 550, 6 550, 6 500 ₽), у 7 — по два кандидата (тонировка тёмное/зелёное, петли 180˚/270˚).

## 2026-09-23 — Поиск товаров без учёта регистра — в приложении, как у клиентов

Владелец попросил искать товары без учёта регистра. Причина та же, что у клиентов (запись от 22.09): база в `SQL_ASCII` с локалью `C`, `ILIKE` не сворачивает кириллицу. Настоящая починка по-прежнему — пересоздать базы в UTF8, это отдельное решение владельца.

## 2026-09-23 — Галерея товара: с сайта забираются все картинки, аватарка — первая

Владелец попросил перенести в ERP все картинки товаров, а не только заглавные. Задел был готов с 22.09 (`ProductImage` — много картинок на товар, порядок `sortOrder`), оставалось использовать его целиком.

- **Импорт (`pnpm import:site-images`) синхронизирует галерею**, а не одну аватарку: порядок картинок в ERP повторяет страницу товара, первая становится аватаркой. Ключ повторного прогона прежний — адрес картинки (`sourceUrl`): что уже лежит, не качается, только переставляется; картинка, убранная с сайта, убирается и в ERP. Решение «файлы в базе» (запись от 22.09) остаётся: бэкап и перенос в бой идут тем же путём, что и данные. Но это уже заметный размер дампа — если картинок станет ещё в разы больше, пора в объектное хранилище.
- **В карточке** — ряд миниатюр: добавить свои (можно выбрать несколько, отправляются по одной — лимит тела Server Action 6 МБ), «Сделать главной», удалить, открыть полный размер. Галерея не редактируется перетаскиванием: порядок задаёт сайт, а человеку нужно лишь выбрать аватарку.

## 2026-09-24 — Описание товара: с сайта текстом, а не HTML

Владелец попросил перенести описания товаров. На сайте они лежат во вкладке «Описание» (`#tab-description` у OpenCart) и набраны в Word: `<o:p>`, классы `MsoNormal`, inline-стили, вложенные `<div>`.

- **Храним текст, не HTML.** Разметка сводится к тексту: абзацы и `<br>` — переводом строки, пункты списков — «• ». Иначе пришлось бы показывать чужой HTML в админке (`dangerouslySetInnerHTML`) и держать санитайзер: описание правится на сайте, и однажды попавший туда скрипт выполнился бы у нас под сессией сотрудника. Текст же без обработки уходит в CSV-выгрузку, в счёт и в коммерческое предложение, а в карточке показывается как есть.
- **Блок описания берётся по балансу `<div>`**, а не по первому `</div>`: внутри описаний свои `<div>`, и разбор обрывался бы на середине.
- **Поле `Product.description`** (`TEXT`, миграция `20260924010000_product_description`). В карточке товара — обычное поле, его можно править руками.
- **Правка руками живёт до следующего прогона `import:site-products`**: каталог синхронизируется с сайта, как название и цена. В форме об этом написано прямо под полем.
- **Нет поля в файле выгрузки — описание не трогаем** (`description` в `siteProductRowSchema` необязательный). Прогон старого `site-products.json`, снятого до 24.09, иначе обнулил бы все описания разом. Явный `null` — описание убрали с сайта, тогда чистим и в ERP.
- **Сущности HTML** раскодируются шире прежнего: типографика Word (`&laquo;`, `&mdash;`, `&sup2;`) и числовые (`&#1057;`). Незнакомую сущность оставляем как есть — лучше «&sup3;» в тексте, чем потерянный символ.

## 2026-09-24 — Админку закрыли от поисковых систем

Владелец спросил, индексируется ли ERP. Проверка живого `erp.bus-com.ru`: заголовка `X-Robots-Tag` **не было** — правило из `Caddyfile` в бою не работает, потому что HTTPS терминирует прокси хостинга (вариант А в `docs/DEPLOY.md`), и до Caddy дело не дошло. В выдаче страниц ERP не нашлось, то есть успели вовремя.

Запрет теперь ставит само приложение — он не зависит от того, что стоит перед ним:

- **`X-Robots-Tag: noindex, nofollow` на все ответы** — `headers()` в `next.config.ts`;
- **`<meta name="robots" content="noindex, nofollow">`** — `metadata.robots` в корневом layout;
- **`/robots.txt` с `Disallow: /`** — `src/app/robots.ts`; маршрут выведен из-под проверки сессии в `src/proxy.ts`, иначе робот получал бы редирект на вход вместо запрета.

Трёх слоёв не жалко: `robots.txt` запрещает обход, но не попадание адреса в выдачу, а `noindex` запрещает именно индексацию. Правило в `Caddyfile` осталось — оно пригодится, если контур переедет на вариант Б.

## 2026-09-24 — Бэкап без байтов картинок ежедневно, картинки — отдельной выгрузкой

Картинки товаров лежат в базе (решение от 22.09), и после переноса галерей их 910 штук на 283 МБ — больше, чем вся остальная база: 322 МБ всего. Полный `pg_dump` весит ~300 МБ: в plain-дампе `bytea` разворачивается в hex, то есть вдвое, а gzip уже сжатые JPEG почти не жмёт. Тридцать дней хранения — около 9 ГБ, на диск сервера в 9,8 ГБ это не влезает. Выяснилось при выкате 24.09: ежедневная выгрузка к тому моменту не делалась ни разу, каталог `/backups` был пуст, то есть требование PRD не выполнялось вовсе.

Разделили по частоте изменения, а не стали переносить файлы в объектное хранилище:

- **ежедневно** — вся база с `--exclude-table-data='"ProductImage"'`, 1,2 МБ, хранение 30 дней. Схема таблицы в дамп попадает, только без строк: иначе выгрузку картинок было бы некуда заливать;
- **раз в неделю** — `--data-only --table='"ProductImage"'`, 322 МБ, хранение 14 дней (две копии).

Картинкам хватает недельного ритма: они меняются только прогоном `import:site-images`, а всё, что приехало с bus-com.ru, в крайнем случае качается оттуда заново. Отдельной выгрузки они заслуживают из-за того, что загружено в карточке товара руками, — это взять больше неоткуда.

**Почему не объектное хранилище.** 283 МБ — не тот объём, ради которого стоит переписывать отдачу картинок на подписанные ссылки, заводить уборку осиротевших файлов (транзакции между базой и бакетом нет) и бэкапить бакет отдельно. Разделение дампа — правка в одном shell-скрипте и решает ровно ту проблему, что была. Возвращаться к хранилищу — когда картинок станет на порядок больше, появится второй сервер приложения или понадобится CDN.

Восстановление теперь из двух файлов по порядку: ежедневный создаёт таблицы, выгрузка картинок их наполняет. Без второго файла ERP работает — просто без картинок товаров.

Владелец попросил хуки на действия и выбор в профиле, о чём получать уведомления: изменение статуса оплаты, новый заказ, каждый этап каждого поставщика.

- **Подписки — массив ключей тем в `User.notificationTopics`** (`src/domain/notification/topics.ts`): `ORDER_CREATED:MANUAL` / `ORDER_CREATED:SITE`, `PAYMENT_STATUS:<статус>`, `SUPPLIER_STAGE:<id этапа>`. Сначала «новый заказ» и «статус оплаты» были одной галочкой каждый; по просьбе владельца разделены, прежние подписки миграция `20260924160000_notification_topics_split` разложила на все части. Галочки «Не оплачен» нет: платежи не удаляются, и вернуться в этот статус заказ не может — галочка никогда бы не сработала. Этап свой у каждого поставщика, поэтому подписка — на id этапа, а не на название. Удалённый этап при следующем сохранении выпадает из подписок; удалить этап с треками нельзя и так.
- **Очередь `Notification`, по строке на получателя.** Хуки (`src/server/notifications/queue.ts`) вызываются внутри той же транзакции, что и изменение: письмо появляется ровно тогда, когда изменение сохранилось. Прямой вызов SMTP из транзакции держал бы её открытой и слал бы письма об откаченном; «отправить после коммита» теряло бы письмо при падении процесса.
- **Отправка — через секунду после хука и таймером раз в минуту** (`dispatch.ts`, запуск из `instrumentation.ts`). Письмо «забирается» условным UPDATE (`claimedAt`), поэтому два процесса на одной базе — например, две машины на общей dev-базе — не шлют его дважды. До 5 попыток, ошибка остаётся в `lastError`.
- **Кому**: активным подписанным, **по всем заказам**, кроме автора изменения — о своём действии он знает. Действия системы (заказ с сайта) уходят всем подписанным. Фильтр «только мои заказы» не делали — не просили.
- **Статус оплаты не хранится**, поэтому хук сравнивает его до и после: в `addPayment` и в `recalculateOrderTotals` — правка состава, скидки или стоимости доставки тоже может сдвинуть «Оплачен» в «Частично». При создании заказа отдельного письма об оплате нет: предоплата с сайта видна в письме о новом заказе.
- **Перенос из прежней ERP не уведомляет** — там хуки не вызываются.
- Возврат этапа в «не начат» не уведомляет: на него нельзя подписаться.

Подсветка просрочки в списке, вкладка «Просроченные», колонка «Просрочен» в CSV и нормативы в справочниках скрыты флагом `SLA_ENABLED = false` в `src/domain/sla.ts`. Старая ссылка с `view=overdue` открывает вид по умолчанию.

Удалять код и поле значило бы миграцию и переписывание при первом же найме менеджера, а флаг включает всё обратно одной строкой и без пересчёта старых заказов. Колонка «В статусе» в списке осталась — сколько заказ висит, видно и без норматива.

## 2026-09-24 — Копия бэкапов вне сервера — на машине владельца

PRD требует копию бэкапа вне машины с базой. Вместо объектного хранилища (rclone в Selectel/Yandex) выбрано скачивание на рабочую машину владельца: `scripts/pull-backups.ps1` по SSH, запуск Планировщиком Windows раз в день. Без новых аккаунтов, ключей и платных сервисов, а объём маленький — 1,2 МБ в день и ~320 МБ картинок в неделю.

Цена — копия свежа, только пока машина включается и VPN не режет сервер. Это приемлемо: на сервере файлы лежат 30 дней, и пропуски догружаются следующим запуском. Скрипт тянет с сервера (pull), а не сервер толкает на машину: у машины нет постоянного адреса, а ключ от сервера на ней уже есть. Если машина владельца перестанет быть надёжной, следующий шаг — тот же скрипт на другой машине или rclone в объектное хранилище с сервера.

Алерт же рассчитан на поток заказов: при ~50 в месяц (2–3 в день) три часа без заказа — обычное дело, и он срабатывал бы почти ежедневно впустую.

## 2026-09-24 — Модели авто — справочник, у товара хранятся названия

Совместимость выбирается из справочника «Модели авто» (`DictionaryItem`, тип `CAR_MODEL`), а не из списка в коде: владелец сам добавляет и переименовывает модели в «Справочниках и настройках», без правки кода и выката. Инфраструктура справочников (редактор, выключение вместо удаления) уже была.

У товара по-прежнему `compatibility String[]` с названиями, а не связь многие-ко-многим с `DictionaryItem`: без миграции данных, без изменения выгрузки CSV и поиска. Цена — название дублируется, поэтому переименование модели переписывает её и у товаров в той же транзакции, а удалить модель, указанную у товаров, нельзя (только выключить). Сервер принимает только модели из справочника и названия, которые уже стоят у товара: старые текстовые значения не ломают сохранение карточки и снимаются руками. Если новому сайту понадобятся слаги и фильтр по модели в SQL — переходить на связующую таблицу.

## 2026-09-24 — Аналитика: выручка — выполненные заказы по дате выполнения

Экран `/analytics` (M7). Выручка за период — сумма итогов заказов, ушедших в «Выполнен» в этом периоде; отменённые и незакрытые не входят (решение владельца). Альтернативы — «все неотменённые по дате создания» (цифра прошлого месяца «доезжала» бы по мере закрытия) и «оплаты по дате платежа» (касса, а не заказы) — отклонены; оплаты показаны отдельной плиткой. Дата выполнения — `statusChangedAt`: «Выполнен» конечный, отдельного поля не заводили. У архивных заказов это дата заказа.

Маржа — сумма `calculateOrderMargin` по заказам, где она известна, с подписью «посчитана по N из M»: у архивных заказов закупки нет, и молча занижать или экстраполировать цифру хуже, чем показать покрытие. Считается в приложении, а не SQL-агрегатом, чтобы не разойтись с карточкой заказа в округлениях комиссии; «Всё время» (~3000 заказов) — около 0,2 с.

Видят руководитель и администратор (`ANALYTICS_ROLES`). Сравнение менеджеров из PRD не делаем — владелец отказался: работают двое на равных. График — разметкой на сервере, без библиотеки графиков.

## 2026-09-25 — Переписка с клиентом: один общий ящик, письма только по кнопке

Владелец попросил вести почтовую переписку с клиентом в ERP с шаблонами «Заказ оплачен» и «Заказ отправлен». Решения:

- **Один ящик на всё — `info@bus-com.ru`.** Заказы с сайта тоже будут приходить туда. Опрос тот же (`src/server/integrations/mailbox.ts`): письмо разбирается один раз, уведомление о заказе с сайта идёт в заказы, любое другое — в `Email`. Второго IMAP-опроса и второго курсора нет. Смена ящика — только переменные `IMAP_*`; новый ящик даёт другой UIDVALIDITY, и опрос сам начнёт с его текущего конца.
- **Привязка входящего — от надёжного к догадке:** Message-ID из In-Reply-To/References совпал с нашим письмом → его заказ; иначе «№ N» или «заказ N» в теме → заказ N; иначе только клиент, если адрес ровно у одного. Голое число в теме не считается (артикул, год). Не привязанное не теряется — раздел «Почта», вкладка «Без заказа», ручная привязка с подсказкой последних заказов клиента.
- **Исходящее сначала уходит по SMTP, потом ложится в базу** с событием заказа в одной транзакции. Обратный порядок оставил бы в переписке письма, которых клиент не получил. Наш Message-ID и References продолжают цепочку последнего письма по заказу (последнего — по времени попадания в ERP, не по заголовку Date: часы у серверов клиентов бывают сбиты).
- **Письма клиенту не уходят автоматически.** Ошибочная оплата или опечатка в треке сразу ушла бы клиенту. Вместо этого подсказка в карточке после полной оплаты и после ввода трека, пока письмо этим шаблоном не отправлено.
- **Отметка «прочитано» у ERP своя**, флаг `\Seen` на письмах клиентов в ящике не ставится: ящик читают и люди.
- **Вложения входящих — в БД** (`EmailAttachment.data`), как счета поставщиков; крупнее 15 МБ не храним, но оставляем строку с причиной. Открываются во вкладке только PDF и картинки без SVG, остальное — скачиванием с `Content-Security-Policy: sandbox`: файлы присылают посторонние, и HTML из письма на нашем домене выполнился бы с сессией сотрудника.
- **Шаблоны — в `Setting` (`emailTemplates`)**, умолчания в коде, как у реквизитов. Строка шаблона, где все подстановки пусты («Трек-номер: {трек}» без трека), выбрасывается целиком.
- **Telegram-бот не делаем, XLSX не делаем** (владелец, 2026-09-24): клиенты в основном в Max, команде хватает писем; CSV открывается в Excel.

## 2026-09-25 — Настройки почты — отдельный раздел, IMAP тоже в интерфейсе

По просьбе владельца SMTP, IMAP и шаблоны писем собраны в «Администрирование → Настройки почты» (`/admin/mail`), из справочников почта ушла. IMAP устроен как SMTP: введённое в интерфейсе главнее переменных `IMAP_*`, пароль в браузер не отдаётся, пустое поле пароля — «оставить прежний». Опрос читает настройки на каждом проходе и таймер запускается, даже пока ящик не задан, — ящик, введённый в интерфейсе, начинает проверяться без перезапуска. Курсор опроса хранит `логин@сервер`: при смене ящика опрос начинает с конца нового, а не продолжает чужую нумерацию UID (курсор без этого поля — от прежней версии, он принимается и дописывается). `IMAP_VIA` и `IMAP_POLL_SECONDS` остались только в окружении — это настройки машины, а не бизнеса.

## 2026-09-25 — Письмо клиента ищет заказ по номеру на сайте

Владелец увидел в бою: ответ на уведомление OpenCart «… - Заказ 2828» привязался к архивному заказу №2828 в ERP, а не к заказу 2828 с сайта. Клиент знает заказ по номеру сайта, поэтому номер в теме теперь ищется так: заказ с сайта с этим номером на сайте (`source = SITE`, `externalId`), иначе заказ, заведённый руками, с этим номером в ERP. Архивные заказы (`LEGACY`) по номеру не ищутся вовсе: их номера прежней ERP пересекаются и с номерами сайта (в dev-базе `2819`, `2820` есть и там и там), и с номерами ERP. Ответы на наши письма это не затрагивает — они находят заказ по цепочке Message-ID.

По той же причине `{номер}` в шаблонах писем стал номером для клиента (на сайте, если заказ с сайта), а номер ERP доступен как `{номер_в_erp}`. Шаблоны выкачены накануне, поэтому смысл подстановки поменян без переименования.

Цитата в ответах клиентов сворачивается (`splitQuotedReply`): хвост из «>»-строк с шапкой перед ним или всё после разделителя Outlook. Цитата посередине письма не трогается, письмо из одной цитаты показывается как есть.

## 2026-09-25 — Номер сайта отдельным полем; импорт истории почты в фоне приложения

**`Order.siteNumber`.** Номер, по которому клиент знает заказ, был только в `externalId` у заказов с сайта; у архивных `externalId` — ID прежней ERP, а номер сайта лежал в примечании «Номер там: N». Заведено поле, миграция заполняет его из обоих источников (проверено на боевой базе в `SQL_ASCII` — регулярка по кириллице работает побайтно: 3017 из 3017). Письмо ищет заказ по `siteNumber` любого источника; номера архива повторяются («10» — у девяти заказов), поэтому берётся самый свежий заказ, созданный за год до письма и не позже дня после.

**Импорт истории** (владелец: 3 года, только с клиентами, вложения названиями, все папки кроме спама/удалённых/черновиков):

- Идёт в фоне внутри процесса приложения — доступ к ящику только у боевого сервера, секреты через разработчика не ходят. Прогресс и курсор по каждой папке — в `Setting` (`mailHistoryImport`); оборванный выкатом импорт продолжается при старте сервера (только в бою), упавший — кнопкой.
- Сначала по пачке из 100 писем читаются конверт, BODYSTRUCTURE и заголовки цепочки; текст скачивается только у писем с клиентами и только текстовой частью (`download` сам снимает base64 и перекодирует в UTF-8). Иначе пришлось бы тянуть гигабайты вложений; на диске сервера свободно ~2 ГБ.
- «С клиентом» — собеседник (отправитель входящего, получатели нашего) есть среди email клиентов. Номер в теме как признак не используется: у поставщиков своя нумерация, и их письма ушли бы в чужие заказы.
- История помечена `importedAt`, сразу прочитана, не попадает во «Без заказа» и не пишет `OrderEvent`: это перенос архива, а не изменение заказа — тысячи строк «Письмо от клиента» завалили бы журнал.
- После импорта — достройка цепочек: письмо без заказа получает заказ другого письма той же переписки, в обе стороны.

## 2026-09-25 — Живой ящик в «Почте»: читаем IMAP, а не копируем

Владелец попросил видеть в «Почте» те же папки, что в Яндексе. Выбран живой просмотр: папки, список писем, письмо и вложения читаются из IMAP при открытии, в ERP ложится только то, что человек сам привязал к заказу. Полная копия ящика (~40 тыс. писем, синхронизация, место на диске) отклонена. Цена — открытие папки или письма занимает секунду-другую (новое соединение на действие; дерево папок кешируется на 30 секунд).

- Действия — по выбору владельца: пометить непрочитанным, переместить в папку, «Удалить». Удаление сделано переносом в «Удалённые» с подтверждением: письмо возвращается, как в Яндексе; окончательное удаление (очистка корзины) из ERP недоступно — единственное необратимое действие с общим ящиком остаётся в почте.
- Открытие письма ставит `\Seen` — как в веб-почте; в «Почте ERP» у переписки своя отметка прочитанности, она не связана с ящиком.
- Ящик видят только HEAD и ADMIN (`MAILBOX_ROLES`): там вся почта компании — банк, бухгалтерия, снабжение.
- Привязка письма из ящика: целиком, с вложениями до 15 МБ и событием в журнале заказа; если письмо уже в ERP (опрос, история) — перепривязка, в том числе наших писем из «Отправленных».
- Попутно найдена и исправлена ошибка: в `folders.ts` флаги IMAP были записаны как `"\Inbox"` — в TypeScript это `"Inbox"`, и системные папки не распознавались (дерево в «Настройках почты» показывало английские имена и не ставило их сверху). Тест совпадал с кодом по той же ошибке; исправлены оба.

## 2026-09-25 — Живой ящик: одно соединение, два кеша папок, «прочитано» только действием

Владелец пожаловался на медленные папки и на две ошибки с отметкой «прочитано». Замеры (в бою: вход в Яндекс 0,18 с, счётчики 22 папок 1,2 с — по запросу STATUS на папку, список без счётчиков 20 мс, 50 писем 0,05–0,9 с в зависимости от прогрева кеша Яндекса) показали, что страницы ждали счётчики, которые нужны только левой колонке, и каждое открытие заново входило в ящик.

- **Одно соединение IMAP на процесс** (`sharedClient`), пересоздаётся при обрыве или смене настроек. У каждой операции — предел 20 секунд: тихо умершее соединение иначе держало бы в очереди все следующие открытия.
- **Два кеша папок:** список без счётчиков (5 минут) — для страниц; счётчики — для левой колонки, устаревшие отдаются сразу, свежие запрашиваются в фоне не чаще раза в 30 секунд. Действия сдвигают счётчики в кеше сразу (по флагу письма, прочитанному перед действием), чтобы колонка в ответе на действие была верной; фоновый пересчёт, начатый до действия, их не перетирает.
- **«Прочитано» ставит только действие при открытии в браузере.** Причин ошибки было две: отрисовка страницы письма сама ставила `\Seen`, а сервер перерисовывает страницу и после «Пометить непрочитанным»; и скачивание текста письма (`BODY[…]`) в папке, открытой на запись, сервер Яндекса помечает прочитанным сам. Теперь письмо читается из папки, открытой только на чтение (EXAMINE), а отметку ставит `markLetterOpened` из браузера.

## 2026-09-25 — Письма не привязываются к заказам: переписка принадлежит клиенту

Владелец отказался от привязки писем к заказам: в заказе нужно видеть переписку с клиентом, последние 10 писем. Поэтому:

- Клиент — единственная привязка письма. Входящее находит клиента по цепочке (клиент письма, на которое отвечают), по номеру заказа на сайте в теме (клиент этого заказа, с окном по дате, как раньше) или по адресу, если он ровно у одного клиента. Иначе письмо ждёт во «Почта → Без клиента» и привязывается поиском по имени, телефону, email или ИНН.
- Переписка клиента собирается запросом: письма с его `customerId` **или** с его адреса, **или** на его адрес. Так подтягиваются письма, пришедшие до того, как адрес вписали в карточку, без пересчёта привязок.
- Письма больше не пишут `EMAIL_RECEIVED` в журнал заказа — это не изменение заказа. Письмо, отправленное из карточки заказа, по-прежнему хранит `orderId` и пишет `EMAIL_SENT`: это действие с заказом, и по нему работают подсказки «Сообщить клиенту?». Ответ из заказа продолжает цепочку последнего письма переписки с клиентом.
- Колонка `Email.orderId` и старые события в журналах остаются — удалять данные незачем, они просто больше не используются для показа.
- Живой ящик: «Привязать к заказу» заменено на «Добавить в переписку» (клиент определяется сам).

## 2026-09-25 — Транспортная накладная: файлы заказа отдельной моделью

Накладная относится к заказу целиком, а не к поставщику, поэтому в `OrderSupplierDocument` (там `supplierId` обязателен) её не положить. Заведена `OrderDocument` с ключом вида (`kind`, сейчас `WAYBILL`) и уникальностью (заказ, вид) — следующие документы заказа (акт, фото упаковки) добавляются строкой в `ORDER_DOCUMENT_LABELS`, без миграции. Проверка файла (по сигнатуре, до 15 МБ) и права — те же, что у счёта поставщика: менять можно, пока заказ не закрыт. Байты — в БД, как у счетов и вложений писем. Своё событие журнала `ORDER_DOCUMENT_CHANGED`, чтобы в истории не путать с файлами поставщика.

## 2026-09-25 — Распознавание накладной локально: Tesseract + штрихкод

Владелец выбрал распознавание без облака (Claude API и Yandex Cloud предлагались: качество выше, но скан с ФИО, телефонами и паспортом уходит внешнему сервису, а оплата — отдельный договор). Цена — ошибки в цифрах на мелких сканах, поэтому:

- **Ничего не сохраняется само.** Кнопка подставляет значения в форму и подсвечивает изменённые поля; сохраняет менеджер, сверившись со сканом. Заполненные поля перезаписываются (решение владельца), кроме адреса: из накладной берётся только город, точный адрес им не затираем.
- **Номер сверяется со штрихкодом.** У «Деловых Линий» номер расписки лежит внутри Code128 вверху бланка; OCR даёт приблизительные цифры, по ним находится окно в штрихкоде (≥60% совпадений, единственное). Без штрихкода номер с мусором не угадывается — поле остаётся как было.
- **Стоимость — «Итог» из накладной** (решение владельца), не «Итого»: итого идёт без страховки.
- Всё внутри процесса Next, по одному распознаванию за раз, воркер на запрос: у сервера одно ядро и 1,5 ГБ, держать воркер (~250 МБ) постоянно дороже, чем секунда на его запуск.
- Модель `rus` 4.0.0_best_int из npm-пакета, а не с CDN по умолчанию: сервер не должен ходить в сеть за моделью, и версия фиксирована lock-файлом.

## 2026-09-25 — Чат сотрудников: опрос вместо сокетов, курсор по `updatedAt`

Владелец попросил общий чат для сотрудников (PRD, M10): один канал, непрочитанные, правка и удаление, вложения на год, ссылки на заказы.

- **Опрос раз в 4 с, а не WebSocket/SSE** (выбор владельца). Пользователей двое-десять, нагрузки нет; постоянное соединение потребовало бы настройки прокси хостинга и переподключений. Опрос — GET `/api/chat/messages`, а не Server Action: действия Next выполняются по очереди, и опрос задерживал бы отправку. Пока вкладка скрыта, лента не опрашивается.
- **Курсор — `updatedAt` с запасом 30 с назад.** По одному курсору приходят и новые, и исправленные, и удалённые. `@updatedAt` ставится до коммита, поэтому сообщение из медленной транзакции может стать видно позже соседа с более поздним временем — без запаса курсор его перепрыгнул бы. Повторы клиент отбрасывает по id и `updatedAt`. Курсор выдаёт сервер (`serverTime`): часам браузера не доверяем.
- **Прочитанность — одна отметка `User.chatReadAt`**, а не запись на каждое сообщение: канал один. Клиент присылает время последнего увиденного сообщения, отметка двигается только вперёд и не дальше «сейчас». Своё сообщение тоже двигает отметку.
- **Удаление мягкое**: строка остаётся с `deletedAt`, текст пустой, вложения удаляются строками — в ленте видно «Сообщение удалено», и опрос узнаёт об удалении по `updatedAt`. Физически — нельзя: удаление не дошло бы до чужих вкладок.
- **Файлы — в БД, как у писем и документов заказа.** Тип определяется по сигнатуре (`detectDocumentType`), неузнанное — `application/octet-stream` и только скачиванием, отдача с `sandbox` и `nosniff`: чужой HTML/SVG на нашем домене не выполнится. Через год байты стираются (`data` = null, `expiredAt`), запись остаётся; таймер раз в 6 часов из `instrumentation.ts` (`src/server/chat/retention.ts`).
- **Ссылки на заказы** разбирает домен (`src/domain/chat/order-links.ts`), а сервер отдаёт только номера существующих заказов — «#1» в шутку не станет битой ссылкой.
- **Значок в меню обновляется сам** (`LiveBadge` в `app-sidebar.tsx`, опрос `/api/chat/unread` раз в 20 с) и гаснет по событию окна `chat-unread`, когда лента отметила прочитанное.

## 2026-09-25 — Пуш-уведомления: Web Push, ключи в настройках

Владелец попросил пуши о новых сообщениях чата на телефоны (Android и iPhone). Сделано стандартным Web Push, без Firebase SDK и без приложения из магазина: ERP ставится на главный экран как PWA (`src/app/manifest.ts`), service worker (`/sw.js`) показывает уведомление.

- **Ключи VAPID — в `Setting` (`push.vapid`), создаются при первом обращении**, а не в `.env`: в бою не нужно ничего заводить руками, и ключи не потеряются при выкате. Смена ключей отвязала бы все подписки, поэтому их нигде не перегенерируем. У dev-базы и боя ключи разные — подписки между ними не переносятся.
- **Service worker отдаётся маршрутом** `src/app/sw.js/route.ts`, а не из `public/`: ему нужна область `/`, а текст удобнее держать в коде. Иконки — в `public/icons`: белый микроавтобус из логотипа сайта (`bus-com.ru/image/catalog/logo/logo-mini.png`) на фирменном зелёном `#008244`, во весь квадрат (Android и iOS скругляют сами), машинка — в безопасном круге maskable. Исходник мелкий (машинка ~120×47), поэтому силуэт увеличен со сглаживанием и порогом; если появится логотип в векторе — перерисовать из него. Та же машинка — в `src/app/favicon.ico` (16/32/48, машинка почти во всю ширину — иначе на 16 px от неё пятно) и в шапке бокового меню (`public/icons/logo-96.png`). Dockerfile теперь копирует `public/` в образ: standalone-сборка его не берёт. `/sw.js`, `/manifest.webmanifest` и `/icons/` открыты без входа (`src/proxy.ts`): браузер запрашивает их без cookie.
- **Адрес подписки — только https известных сервисов пушей** (Google, Apple, Mozilla, Microsoft; `isPushServiceHost`). Сервер шлёт на этот адрес запросы, и без проверки любой сотрудник заставил бы ERP ходить на произвольный адрес, в том числе внутрь сети.
- **Отправка — после ответа (`after` из `next/server`), без очереди и повторов.** Опоздавший пуш о сообщении чата бесполезен, а само сообщение видно в ленте. Ответ 404/410 от сервиса — подписка удаляется; прочие ошибки — в лог. TTL сутки, `topic`/`tag` = «chat»: пока телефон вне сети, копится одно уведомление, а не пачка.
- **Подписка переходит к тому, кто включил её последним**: на общем компьютере уведомления получает вошедший сотрудник. Страница настроек при открытии напоминает серверу о подписке браузера — если её удалили на сервере, она восстановится.

## 2026-09-25 — Мобильная версия: та же страница, другая раскладка ниже `md`

Исследование на 390 px (`docs/MOBILE-PLAN.md`) показало: карточка заказа в 2,5 раза шире экрана, списки — таблицы с прокруткой вбок, кнопки 26–28 px. Отдельную мобильную версию не делали — те же страницы и Server Actions, раскладка меняется классами Tailwind.

- **Диалоги на телефоне — шторка снизу** для всех сразу (в `dialog.tsx`): кнопки под пальцем, длинная форма прокручивается внутри.

- **Нижнее меню прячется на карточке заказа**: там своя панель действий, две панели внизу съели бы экран.
- **«Потянуть — обновить» только в режиме приложения** (`display-mode: standalone`): в браузере жест есть свой, и двойное обновление мешало бы.
- **Сенсорный ввод определяется `pointer: coarse`, а не шириной экрана**: у планшета широкий экран, но нет наведения — меню «…» в чате должно быть видно и там.

## 2026-09-25 — Доставка не входит в сумму заказа

Владелец: доставку клиенты оплачивают транспортным компаниям отдельно, в сумме заказа ей не место. Раньше `calculateOrderTotals` прибавлял её к итогу — из-за этого счёт и статус оплаты требовали с клиента деньги, которые он платит не нам.

- **Итог = товары со скидками − скидка на заказ.** Поле `deliveryPriceKopecks` осталось: стоимость видна в «Доставке» и справкой под итогами («в сумму не входит»). Маржа доставку и раньше не учитывала — там ничего не поменялось.
- **Счёт PDF** больше не печатает строку «Доставка»: «Итого к оплате» — то, что клиент платит нам.
- **Заказ с сайта:** «Итого» OpenCart включает доставку, поэтому для пометки «сумма с сайта не совпала» сравниваем с `totalKopecks + deliveryPriceKopecks`. Иначе каждый заказ с доставкой получал бы ложное предупреждение.
- **Старые заказы пересчитаны миграцией** `20260925230000_delivery_out_of_total` (только данные): итог уменьшен на доставку, в журнал каждого такого заказа — запись с суммами до и после. Статус оплаты не хранится, он пересчитается сам. В бою на момент решения доставка была у одного заказа, открытого и оплаченного частично — переплаты не возникло.

## 2026-09-25 — Ответы в чате: ссылка на сообщение, цитата собирается при выборке

`ChatMessage.replyToId` — ссылка на исходное (миграция `20260926000000_chat_replies`). Текст цитаты не копируется в ответ: сервер собирает её при каждой выборке (`replyPreview`), поэтому исправление или удаление исходного видно и в цитате. Цена — цитата у уже открытой ленты обновляется только при перезагрузке: опрос по `updatedAt` приносит исходное, но не ответы на него. Для двух-десяти человек это не стоит усложнения курсора. `onDelete: SetNull` — страховка: сообщения удаляются мягко, строка остаётся.

## 2026-09-26 — «Отправленные» ящика: копия писем ERP и опрос папки

Владелец: письма клиентам должны лежать и в «Отправленных» ящика, а письма, написанные в веб-почте мимо ERP, — попадать в переписку клиента (её видно в карточке заказа).

- **Копия — IMAP APPEND того же текста, что ушёл по SMTP.** `sendClientLetter` собирает письмо один раз (`streamTransport` nodemailer) и отправляет готовым (`raw` + конверт), текст возвращается и кладётся в папку с флагом `\Seen`. Одна сборка — один Message-ID и в базе, и в ящике. Копия делается в `after()` действия: письмо уже ушло и сохранено, сбой копии только пишется в лог и не превращается в «не отправлено».
- **Опрос читает «Отправленные» вторым проходом** со своим курсором (`sentEmailCursor` в `Setting`); папка — по флагу `\Sent`, иначе по имени. Первый проход запоминает конец папки: прежние письма переносит импорт истории. Наши копии узнаются по Message-ID и второй раз не заводятся.
- **В переписку ложится только письмо клиенту:** ответ в цепочке, где клиент известен, или письмо на адрес ровно одного клиента. Номер заказа в теме здесь не учитывается — такие темы бывают у писем поставщикам, а они клиенту не показываются. Остальное из «Отправленных» пропускается, во «Без клиента» не попадает.
- Если Яндекс сам начнёт класть копии писем, ушедших по SMTP, в ящике будет два экземпляра; в ERP — по-прежнему один.

## 2026-09-26 — Сайт: слуги, метатеги и переадресации из снимка старого сайта

Этап 2 плана сайта. Снимок старого OpenCart — в репозитории (`docs/site-snapshot/`, `pnpm snapshot:old-site`): после переключения DNS старый сайт ничего не отдаст, а по снимку проверяется, что ни один старый адрес не отдаёт 404.

- **Слуг — поле товара и категории** (`Product.slug`, `ProductCategory.slug`, уникальные), а не отдельная таблица адресов. Товары и категории живут на одном уровне `bus-com.ru/{slug}`, как на старом сайте, поэтому слуг уникален на весь сайт — это проверяет план импорта (`src/domain/site/seo-import.ts`); база держит уникальность только внутри таблицы.
- **Слуг берётся из canonical старой страницы**, дословно, даже 158-значный. У 14 товаров canonical был `index.php?…product_id=N` — им слуг построен транслитерацией названия (`src/domain/site/slug.ts`, до 80 знаков по границе слова), старый адрес ведёт на новый 301.
- **Метатеги — дословно** (`metaTitle`, `metaDescription`): у 197 из 215 товаров title написан руками и из названия не выводится.
- **`UrlRedirect` ссылается на товар или категорию, а не на путь.** Переадресация ведёт на _текущий_ слуг, так что смена слуга в ERP старые ссылки не ломает. `toPath` — только для целей вне каталога (главная). Удалили товар — ссылка обнуляется (`SetNull`) и адрес ведёт на главную, а не в 404. 410 — `/refubrishment_test`.
- **Категории сопоставлены по названию и родителю**: id OpenCart в ERP не сохранялся, а названия справочника взяты из того же меню сайта. Родителя берём из любого адреса категории с крошками — по короткому адресу OpenCart крошек не отдаёт. Категория, которой в ERP нет, ведёт на родителя (`/kondicionery` → «Климат»), без родителя — на главную (`/paz`, переоборудование).
- **`/paz` временно ведёт на главную.** По сути это подборка товаров под ПАЗ, а не категория; на этапе 7 (подбор по модели) переадресацию перевести на страницу модели.
- **Импорт повторяем**: слуг и метатеги, уже заданные в ERP, не перезаписываются — их могли поправить руками; переадресации узнаются по `fromPath`.
