# Общая база разработки

Разработка идёт с двух машин, и на каждой была своя локальная база — состояния расходились, а миграции приходилось накатывать дважды. Теперь база одна и живёт на сервере: что видно на одной машине, то видно и на другой.

**Заведена 2026-09-21.** Решение и его цена — `docs/DECISIONS.md`, запись «Общая dev-база — вторая база в боевом Postgres».

## Как устроено

|                |                                                                         |
| -------------- | ----------------------------------------------------------------------- |
| Сервер         | тот же, что боевой: Джино.VPS, контейнер `buscom-erp-postgres-1`        |
| База           | `buscom_erp_dev` (боевая рядом — `buscom_erp`, это **другая** база)     |
| Роль           | `buscom_dev`, владелец `buscom_erp_dev`                                 |
| Доступ         | только по SSH-туннелю, порт Postgres опубликован на `127.0.0.1` сервера |
| Локальный порт | `5433` — чтобы не мешать нативному Postgres на 5432                     |

Боевая и dev-база делят один процесс Postgres. Изоляция — правами, а не отдельным сервером:

- `REVOKE CONNECT ON DATABASE buscom_erp FROM PUBLIC` — роль `buscom_dev` в боевую базу **не войдёт**, проверено: `FATAL: permission denied for database "buscom_erp"`;
- приложение в бою ходит под ролью `buscom` и правки не заметило.

Чего изоляция не даёт: ядро на сервере одно и память общая. Тяжёлый импорт или сид по dev-базе отнимает ресурсы у живой ERP. Разовые скрипты на тысячи строк лучше гонять по локальной базе (она осталась как запасной путь) и переносить результат дампом.

## Настроить на новой машине

**1. Ключ и запись в `~/.ssh/config`**

Ключ доступа к серверу — тот же, которым ходит деплой (`buscom_deploy` / `id_ed25519_buscom`, имя на машинах разное). Если его нет, добавить публичную часть пользователю `deploy` на сервере.

```
Host buscom-prod
  HostName ba5699d52128.vps.myjino.ru
  Port 49265
  User deploy
  IdentityFile ~/.ssh/buscom_deploy
  IdentitiesOnly yes
```

Имя `buscom-prod` — не произвольное: его ищет `scripts/db-tunnel.ts`. Проверка: `ssh buscom-prod "echo ok"`.

Адрес сервера и порт держатся в `~/.ssh/config`, а не в репозитории: репозиторий публичный.

**2. `DATABASE_URL` в `.env`**

```dotenv
DATABASE_URL="postgresql://buscom_dev:<пароль>@localhost:5433/buscom_erp_dev?schema=public"
```

Пароль роли `buscom_dev` — у владельца проекта, в репозиторий не попадает. Забыт — задать заново с сервера:

```bash
ssh buscom-prod "docker exec -i buscom-erp-postgres-1 psql -U buscom -d postgres" <<'SQL'
ALTER ROLE buscom_dev PASSWORD 'новый-пароль';
SQL
```

**3. Проверить**

```bash
pnpm db:tunnel                 # в отдельном окне, оставить работать
pnpm prisma migrate status     # ждём «Database schema is up to date!»
```

## Каждый день

Туннель нужен всегда, когда работает `pnpm dev`, `prisma migrate`, `prisma studio` или скрипты импорта:

```bash
pnpm db:tunnel   # отдельное окно; Ctrl+C — закрыть
pnpm dev
```

Скрипт переподнимает связь сам, так что спящий режим и смена сети туннель не роняют. Второй туннель запускать не нужно — скрипт видит занятый порт и отказывается.

Симптом забытого туннеля: `P1001`, не удаётся подключиться к `localhost:5433`.

## Работа без сети

Туннель требует связи с сервером, а её не всегда есть. Локальная база осталась на месте — `pnpm db:pull` заливает в неё текущее состояние общей:

```bash
pnpm db:pull     # туннель при этом должен работать
```

Дальше переключаешь `DATABASE_URL` в `.env` на закомментированную локальную строку и работаешь без сети. Вернулся — переключаешь обратно; всё, что наработано в локальной копии, в общую базу само не уедет.

Куда класть копию, берётся из `LOCAL_DATABASE_URL`. Скрипт откажется писать куда-либо, кроме `localhost`, и на порт источника — перепутать общую базу с локальной он не даст.

Обратной команды `db:push` намеренно нет: залить свою базу поверх общей — значит стереть работу второй машины. Нужно перенести сделанное — переноси данными (заказ, товар), а не целой базой.

## Миграции на общей базе

База одна на двоих, схема тоже. Порядок обычный, но с оглядкой:

- новая миграция — `pnpm db:migrate` на той машине, где правишь `schema.prisma`;
- на второй машине после `git pull` — `pnpm db:deploy`, своя миграция там не нужна;
- **`prisma migrate reset` и `db push --force-reset` теперь стирают общую базу, а не свою**. Это и раньше было запрещено без явной просьбы (CLAUDE.md), теперь цена ошибки выше: пропадёт и работа второй машины.

Правка `schema.prisma` без миграции у одного и накат у другого разойдутся — Prisma на второй машине увидит drift. Лечится обычным `pnpm db:migrate` после `git pull`.

## Тесты остались локальными

Интеграционные тесты чистят базу через `TRUNCATE` и идут только по базе, в имени которой есть `test` (`src/test/db.ts`). В имени `buscom_erp_dev` слова `test` нет, поэтому общую базу они не тронут при любой ошибке в настройках — защита сработает раньше. Для прогона с БД по-прежнему нужна локальная тестовая база и `RUN_DB_TESTS=1`.

## Бэкапов у неё нет

`scripts/backup-db.sh` выгружает только боевую `$POSTGRES_DB`. Dev-база не выгружается сознательно: это рабочее состояние разработки, а не данные компании, и место на сервере (свободно ~3.4 ГБ) тратить на неё незачем.

Наполнить заново — дампом с любой машины:

```bash
pg_dump --no-owner --no-acl --clean --if-exists -f dump.sql "<локальный DATABASE_URL>"
psql -v ON_ERROR_STOP=1 -f dump.sql "postgresql://buscom_dev:<пароль>@localhost:5433/buscom_erp_dev"
```

Или копией боевой — целиком внутри сервера, по сети ничего не едет:

```bash
ssh buscom-prod "docker exec buscom-erp-postgres-1 sh -c \
  'pg_dump -U buscom -d buscom_erp --no-owner --no-acl | psql -U buscom -d buscom_erp_dev'"
```

Копия боевой означает реальные ПДн клиентов на машине разработки в открытом виде. Держать такую копию дольше, чем нужно для проверки, не стоит.

## Что откуда взялось

База — копия боевой (перезалита 22.09.2026): 3019 заказов, 4342 клиента, 221 товар, 215 картинок, 3 поставщика.

Первая заливка (21.09) шла с локальной базы первой машины, и это стоило работы второй: четыре действующих заказа «В работе», перенесённых из прежней ERP руками, пропали, а под их номерами оказались демо-заказы. Восстанавливали из боевой базы — она к тому моменту была единственным местом, где эта работа сохранилась.

**Вывод на будущее: перед тем как заливать общую базу поверх, проверь, не осталось ли на второй машине несохранённой работы.** В git её нет — данные живут только в базе.

Перезаливка из боевой делается так (всё внутри сервера, по сети ничего не едет):

```bash
ssh buscom-prod "docker exec -i buscom-erp-postgres-1 psql -U buscom -d postgres" <<'SQL'
SELECT pg_terminate_backend(pid) FROM pg_stat_activity
  WHERE datname = 'buscom_erp_dev' AND pid <> pg_backend_pid();
DROP DATABASE "buscom_erp_dev";
CREATE DATABASE "buscom_erp_dev" OWNER buscom_dev;
REVOKE CONNECT ON DATABASE "buscom_erp_dev" FROM PUBLIC;
GRANT CONNECT ON DATABASE "buscom_erp_dev" TO buscom_dev;
SQL

ssh buscom-prod "docker exec buscom-erp-postgres-1 sh -c   'pg_dump -U buscom -d buscom_erp --no-owner --no-acl    | psql -q -v ON_ERROR_STOP=1 -U buscom_dev -d buscom_erp_dev'"

pnpm prisma migrate deploy   # миграции, которых в бою ещё нет
```

Базу обязательно пересоздавать с владельцем `buscom_dev` и заливать под ним же. Если залить под `buscom`, таблицы достанутся суперпользователю и роль разработки потеряет доступ к собственной базе.

Перед перезаливкой имеет смысл снять точку отката — `pg_dump` dev-базы в `/tmp` на сервере.

## Что должно доехать до `main`

Публикация порта Postgres на loopback живёт в `docker-compose.prod.yml`. На сервере она **сейчас применена правкой файла на месте**, а деплой делает `git reset --hard origin/main` — то есть первый же выкат из `main` без этой правки уберёт порт и сломает туннель.

Пока изменение не влито в `main`, после каждого выката порт надо возвращать:

```bash
ssh buscom-prod "cd /opt/buscom-erp && \
  sed -i 's|    expose:|    ports:\n      - \"127.0.0.1:5432:5432\"\n    expose:|' docker-compose.prod.yml && \
  docker compose -f docker-compose.prod.yml --env-file .env.production up -d postgres"
```

Адрес `127.0.0.1` в публикации обязателен. Без него Docker пропишет правило в iptables в обход `ufw`, и боевая база окажется открыта в интернет.
